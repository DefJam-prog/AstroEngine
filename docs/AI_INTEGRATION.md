# Codex / AI Integration и безопасность

Статус: AI-assisted authoring закреплён как ключевая часть цели AstroEngine. Подэтап 09.1 добавил in-process C++ фасад `AIEditorApi` и каталог схем реально зарегистрированных команд. Адаптер Codex, process/JSON transport, sandbox и AI Game Tester не реализованы. Фасад не является границей безопасности и не предоставляет доступа к файловой системе, секретам или сети.

## Граница интеграции

AI Editor API доступен локально через типизированные команды. Для Codex предусматривается отдельный адаптер. AI — один из главных авторских workflows продукта; при этом подключение AI adapter/provider не требуется для запуска игры или редактора. Это не снижает приоритет AI-разработки, а отделяет её от runtime-зависимостей и конкретного поставщика.

AI не изменяет внутреннее состояние сцен в обход команд. Общие контракты команд, транзакций и ограничений обратимости определены как требования в [ARCHITECTURE.md](ARCHITECTURE.md).

### Реализованный локальный фасад (09.1)

`astro::core::AIEditorApi` получает ссылку на зарегистрированный `CommandRegistry`, сообщает версию фасада (1.0), возвращает детерминированный каталог схем и предоставляет typed `validate`/`execute`. Выполнение делегируется исходному registry: применяются его валидаторы, аудит и история транзакций. Каталог перечисляет только установленные при запуске команды; это не обещание полного набора операций движка. Текущие Scene-команды и поля описаны в [COMMAND_API.md](COMMAND_API.md).

После 04.14 каталог Scene-команд содержит `entity.set_property`, `entity.set_sprite_renderer` и `script_behavior.add`, `script_behavior.set_enabled`, `script_behavior.remove`. Поэтому AI caller может авторить C# binding теми же undoable commands, что и Inspector. Командный Scene-слой проверяет структуру ссылки, но не текущий project build; Editor runtime consent capture проверяет полный script set и свежие build hashes перед любым Play load.

Это библиотечный API внутри процесса редактора. У него нет сетевого или JSON протокола, динамического разбора payload, отдельной модели разрешений или подтверждения пользователя. In-process callers должны считаться доверенным кодом; API нельзя выставлять наружу как защищённый endpoint.

## Возможности по мере развития

- Чтение дерева проекта и анализ сцен.
- Создание и изменение объектов, материалов, UI, графов логики и шаблонов игр.
- Предложение изменений, тестирование и составление отчётов.
- Изменение C# исходников — только с понятным файловым diff; запуск/сборка обновлённого кода проходит разрешения, явное подтверждение для рискованных действий и тесты.

Эти возможности вводятся по мере готовности необходимых подсистем, в явно назначенных подэтапах. Изменения шаблонов подчиняются требованиям [GAME_TEMPLATES.md](GAME_TEMPLATES.md).

## Пайплайн операции

Запрос → план → проверка схемы и разрешений → dry-run/diff → подтверждение для рискованных операций → транзакция → тесты → отчёт.

Применимость dry-run и обратимость конкретной команды должны быть документированы. Наличие этапа транзакции не означает, что любое runtime-действие можно отменить. Контрольные точки и откат AI-изменений следуют P09 из [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md).

## Ограничения доступа и выполнения

AI не получает неограниченного доступа к файловой системе, секретам и сети. Требуются:

- Список разрешённых директорий.
- Sandbox для сборок и тестов.
- Журнал действий.
- Контроль затрат и времени.
- Возможность остановки долгих операций.

Конкретный локальный транспорт, механизм разрешений, изоляция процессов, политика доступа к секретам и сети, лимиты и механизм остановки пока не выбраны. Локальность API сама по себе не подтверждает изоляцию. Эффективность ограничений должна быть проверена при реализации.

## AI Game Tester

Требуются детерминированные сценарии ввода и проверки коллизий, прохождения уровней, поведения транспорта и save/load; сбор логов и скриншотов, поиск регрессий.

Не обещать, что AI гарантирует отсутствие ошибок. Отчёты должны указывать выполненные сценарии, результаты и ограничения проверки.

Предложения оптимизации проверяются на изменения поведения и визуальные отличия. Исходные пользовательские ресурсы сохраняются при генерации оптимизированных копий.

Будущая работа AI с C# исходниками не означает доверенное или автоматически безопасное исполнение сгенерированного кода. Проектные скрипты должны рассматриваться как обычный код с правами процесса до появления отдельно проверенной изоляции.

### Разрешение на запуск C# в Play Mode (04.11, политика)

Перед будущей загрузкой скриптов Play Mode Editor должен собрать все enabled `ScriptBehavior` текущей Scene, разрешить каждую привязку и подтвердить актуальные build hashes. До загрузки CLR/assembly пользовательский диалог показывает точный набор: project и Scene, AssetId, source path, managed type, build fingerprint и идентификатор/хеш output generation. Подтверждение действует только на этот набор и одну Play-сессию; Stop или повторный Play требует нового согласия. Смена project/Scene, состава скриптов, manifest, source, assembly или runtimeconfig hash до загрузки инвалидирует его. После прямого подтверждения Editor повторно разрешает весь набор и сравнивает его с показанным snapshot непосредственно перед host load; любое расхождение прекращает запуск. Missing/stale/invalid binding и отмена блокируют весь script-set до lifecycle callbacks; ошибки не допускают частичного вызова компонентов. Hot reload в этом контракте отсутствует: изменения на диске относятся к следующему Play.

Согласие не сохраняется как повторно используемое доверие в project manifest, scene или user settings. Codex, AI Editor API, CLI, build success и тестовый отчёт не могут самостоятельно его выдать. AI может запросить Play-проверку, после чего ожидать прямого действия пользователя в Editor. Editor gate реализован в 04.12; 04.13 подключает его к Play: перед каждой уникальной host-загрузкой runtime повторно сверяет точный snapshot, затем запускает lifecycle enabled ScriptBehavior. Это UX/accidental-execution policy, не security sandbox: загруженный C# получает права текущего процесса, включая доступные ОС API/файлы/сеть. Низкоуровневая C++ функция `CSharpScriptHost::loadScriptAsset` сама не содержит permission gate и предназначена для доверенного использования и тестов.

## Будущая проверка реализации

При реализации соответствующих подэтапов проверить пайплайн команд, отклонение недопустимых схем и неразрешённых действий, подтверждение рискованных операций, ограничения директорий/секретов/сети, изоляцию сборок и тестов, аудит, лимиты и остановку. Проверить запуск игры и редактора без AI-интеграции и повторяемость детерминированных сценариев тестера.

Зависимости: Typed Command API, схемы, модель проекта/сцены, транзакции, диагностика и тестовая инфраструктура. Конкретные SDK, модели, протоколы и версии не выбраны. Исполняемых тестов и подтверждений безопасности пока нет.

### C# worker security boundary prototype (04.19)

The standalone Windows metadata-validator currently has no AI or Editor caller. Any later caller must preserve its bounded protocol and AppContainer policy; an AI request cannot grant capabilities, widen project paths, or bypass consent. Integration and project-root path validation are not implemented. The metadata reader is not certified for hostile PE, and the existing C# runtime host is still in-process/trusted-code-only. See [D084](DECISIONS.md#d084--windows-c-metadata-validator-worker-prototype-0419) and [04.19 report](reports/04.19-csharp-metadata-validator-worker.md).
