# Codex / AI Integration и безопасность

Статус: AI-assisted authoring закреплён как ключевая часть цели AstroEngine. Подэтап 09.1 добавил in-process C++ фасад `AIEditorApi`; 09.2 добавил read-only контекст активной загруженной сцены и проверку описательных планов. Это локальные C++ API для доверенного кода. Полное дерево проекта, process/JSON transport, sandbox и AI Game Tester не реализованы. Адаптер не является границей безопасности и не предоставляет доступа к файловой системе, секретам или сети.

## Граница интеграции

AI Editor API доступен локально через типизированные команды. Для Codex предусматривается отдельный адаптер. AI — один из главных авторских workflows продукта; при этом подключение AI adapter/provider не требуется для запуска игры или редактора. Это не снижает приоритет AI-разработки, а отделяет её от runtime-зависимостей и конкретного поставщика.

AI не изменяет внутреннее состояние сцен в обход команд. Общие контракты команд, транзакций и ограничений обратимости определены как требования в [ARCHITECTURE.md](ARCHITECTURE.md).

### Реализованный локальный фасад (09.1)

`astro::core::AIEditorApi` получает ссылку на зарегистрированный `CommandRegistry`, сообщает версию фасада (1.0), возвращает детерминированный каталог схем и предоставляет typed `validate`/`execute`. Выполнение делегируется исходному registry: применяются его валидаторы, аудит и история транзакций. Каталог перечисляет только установленные при запуске команды; это не обещание полного набора операций движка. Текущие Scene-команды и поля описаны в [COMMAND_API.md](COMMAND_API.md).

После 04.14 каталог Scene-команд содержит `entity.set_property`, `entity.set_sprite_renderer` и `script_behavior.add`, `script_behavior.set_enabled`, `script_behavior.remove`. Поэтому AI caller может авторить C# binding теми же undoable commands, что и Inspector. Командный Scene-слой проверяет структуру ссылки, но не текущий project build; Editor runtime consent capture проверяет полный script set и свежие build hashes перед любым Play load.

Это библиотечный API внутри процесса редактора. У него нет сетевого или JSON протокола, динамического разбора payload, отдельной модели разрешений или подтверждения пользователя. In-process callers должны считаться доверенным кодом; API нельзя выставлять наружу как защищённый endpoint.

### Codex project context и описательный план (09.2)

При `ASTRO_BUILD_AI_EDITOR_API=ON` собирается отдельная библиотека `astro_ai_editor`; тестовая конфигурация также собирает её, когда `BUILD_TESTING=ON`. Runtime/editor без тестов не включает adapter по умолчанию. `astro::ai::CodexProjectAdapter` получает `AIEditorApi` и может:

- вернуть копию переданной ему активной загруженной Scene: ID/имя сцены, сущности с ID/именем/родителем, Transform и список известных типов компонентов с ID и schema version;
- вернуть вместе с этим только фактически зарегистрированные схемы команд;
- проверить описательный план версии 1: ограничение размера summary и числа шагов, уникальные step ID, непустые намерения, зарегистрированные command ID и актуальные версии схем.

Снимок детерминированно сортируется по Entity ID и типам/ID компонентов. Источник — объект Scene в памяти; adapter не открывает каталог проекта и не обходит файловую систему. План не содержит типизированных payload и не может быть выполнен через этот adapter. Natural-language model/Codex transport отсутствует. Ошибки содержат причину для caller. Эти ограничения намеренны: построение diff, согласие пользователя, динамический transport и выполнение относятся к следующим подэтапам.

### Read-only typed property preview (09.3a)

`previewSetProperty(scene, commandSchemaVersion, payload)` поддерживает только `entity.set_property`. Он требует, чтобы эта версия команды была зарегистрирована как transactional, считывает старое значение из переданной Scene, валидирует новое значение её Property schema и возвращает typed `before`/`after`, identity и флаг `changesValue`. При невалидном entity/property/value или устаревшей версии возвращается ошибка. Никакие данные не записываются.

### Editor approval и применение (09.3b–09.3g)

В панели **AI Change Review** Editor показывает имя выбранной сущности, предложение и typed diff до/после. Пользователь может отменить preview или нажать **Confirm and apply**. Подтверждение доступно только при открытом проекте. Перед исполнением review model проверяет совпадение project/scene identities и Scene ID, заново вычисляет preview на текущем состоянии и отказывает, если before/after устарели или значение больше не изменяется. После этого она вызывает существующую transactional-команду `entity.set_property` через `AIEditorApi`; команда сохраняет обычные валидацию, аудит и Undo/Redo. Успешное применение помечает сцену как изменённую.

В 09.3c тот же flow расширен на изменение видимости существующего `SpriteRenderer` через `entity.set_sprite_renderer`. Предложение сохраняет AssetId; до подтверждения повторно сверяются component ID, AssetId и исходное значение visibility. UI не создаёт компонент и не подбирает новый ресурс. Undo/Redo остаются ответственностью исходной транзакционной команды.

В 09.3d панель позволяет подготовить создание встроенного 3D-примитива через уже существующую transactional-команду `entity.create_primitive`: пользователь задаёт имя, форму (Cube/Plane/Sphere/Cylinder), видимость и выбирает, будет ли выбранная сущность родителем. Preview показывает ожидаемый следующий Entity ID и параметры, не меняя Scene. До подтверждения review повторно проверяет project/scene identity, Scene ID, ожидаемый ID и все параметры; затем выполняется обычная команда, возвращается созданный Entity ID, а undo/redo и сохранение используют существующий путь движка. Создание геометрии не записывает пользовательские asset-файлы.

В 09.3e добавлен узкий review для создания `Camera3D` на выбранной сущности. Preview только проверяет зарегистрированную версию транзакционной команды `camera3d.add`, валидирует целевую сущность и формирует предложение; Scene не меняется. Подтверждение повторно сверяет корень проекта, путь сцены, Scene ID и существование цели, затем вызывает ту же команду через `AIEditorApi`. Добавленная перспективная камера по умолчанию неактивна, чтобы не менять Game View неожиданно. Unit-тесты проверяют устаревшую цель/проект, Undo/Redo и Cancel, а оконный smoke сохраняет и повторно загружает сцену. См. [отчёт 09.3e](reports/09.3e-camera-addition-review.md).

В 09.3f review расширен только на параметры объектива уже существующей Camera3D через `camera3d.set_lens`: вертикальный FOV, near и far. Preview сохраняет Component ID, исходные/новые значения и active-флаг. Перед применением сравнивается весь snapshot, чтобы не перезаписать внешнее изменение или заменённый компонент; вызов остаётся за транзакционной командой, которая сохраняет ID и active-флаг. Если камера активна, UI явно предупреждает, что новый объектив изменит Game View; переключать active camera этот срез не умеет. Unit-тест покрывает no-op, устаревшие значения, Undo/Redo и отмену; окно редактора сохраняет активную камеру и проверяет новые параметры после повторной загрузки. См. [отчёт 09.3f](reports/09.3f-camera-lens-review.md).

В 09.3g review разделяет два намеренных действия над активным выбором: «активировать выбранную Camera3D» и «очистить активную камеру». Read-only preview показывает текущую камеру и целевую (или «нет активной»), включая предупреждение о последствиях для Game View. Подтверждение повторно сверяет project/scene identity, Scene ID, предыдущую Entity/Component identity и целевую Camera3D Component ID, затем делегирует исполнение `camera3d.set_active`. Stale и no-op preview отклоняются; транзакция сохраняет Undo/Redo, а оконные smokes подтверждают переключение/очистку и повторную загрузку сцены. Очищается активная камера редактируемой сцены: Play Mode использует runtime-копию и не теряет свою камеру. См. [отчёт 09.3g](reports/09.3g-camera-selection-review.md).

#### 09.3h–09.3j — Transform в AI Change Review

В 09.3h AI review Transform был отложен: Transform задавался прямым `Scene::setTransform`, а отдельной typed-транзакции не было. В 09.3i добавлена команда `entity.set_transform` v1; `entity.set_property` по-прежнему отвечает только за имя.

Команда принимает весь Transform как локальные `position`, `rotationDegrees`, `scale`, проверяет его через существующую Scene-валидацию, сохраняет Component ID и делегирует изменение/Undo/Redo транзакции. В 09.3j панель AI Change Review редактирует девять чисел и показывает local before/after. Для Camera3D дополнительно вычисляет world position, target и up на копии Scene. Preview записывает Scene/Entity/Component IDs, исходный Transform и цепочку родителей с их Transform IDs, локальными значениями и связями. Подтверждение отклоняется, если целевой Transform, parent link или любой ancestor изменился; иначе вызывает `entity.set_transform`. Нулевые масштабы не запрещены новой бизнес-логикой; если вычисление мировой позы невозможно, UI сообщает об этом, не подменяя локальные значения. См. [09.3h assessment](reports/09.3h-transform-contract-assessment.md), [09.3i](reports/09.3i-transform-command.md) и [09.3j](reports/09.3j-transform-review.md).

Это ограниченный review для имени, видимости существующего SpriteRenderer, создания встроенного примитива, Camera3D, локального Transform и смены родителя, а не универсальный UI для всех typed payload. Отмена удаляет pending preview. Review model живёт в доверенном процессе редактора и не является OS/security boundary. JSON/IPC, модель permissions и allowlist, sandbox, checkpoints, общий rollback и тестирование произвольных команд остаются будущей работой.

#### 09.3k — изменение родителя сущности

Панель предлагает выбрать корень или допустимого родителя и до подтверждения показывает before/after, размер поддерева и производную мировую позу Camera3D, если она есть. Команда `entity.reparent` v1 меняет только ссылку родителя: локальные Transform и связи потомков сохраняются, мировая поза следует новой иерархии. Adapter snapshot охватывает исходную цепочку, целевую цепочку и каждую сущность перемещаемого поддерева; подтверждение пересоздаёт preview и отвергает любое расхождение, no-op и циклы. Применение делегируется транзакции с Undo/Redo. Режима сохранения мировой позы нет. Это конкретная операция AI Change Review внутри Editor, не общий механизм разрешений и не security boundary. См. [09.3k report](reports/09.3k-entity-reparent-review.md).

## Возможности по мере развития

- Чтение дерева проекта и анализ сцен.
- Создание и изменение объектов, материалов, UI, графов логики и шаблонов игр.
- Предложение изменений, тестирование и составление отчётов.
- Изменение C# исходников — только с понятным файловым diff; запуск/сборка обновлённого кода проходит разрешения, явное подтверждение для рискованных действий и тесты.

Эти возможности вводятся по мере готовности необходимых подсистем, в явно назначенных подэтапах. Изменения шаблонов подчиняются требованиям [GAME_TEMPLATES.md](GAME_TEMPLATES.md).

## Пайплайн операции

Запрос → план → проверка схемы и разрешений → dry-run/diff → подтверждение для рискованных операций → транзакция → тесты → отчёт.

Применимость dry-run и обратимость конкретной команды должны быть документированы. Наличие этапа транзакции не означает, что любое runtime-действие можно отменить. Контрольные точки и откат AI-изменений следуют P09 из [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md).

## Ограничения доступа и выполнения

AI не получает неограниченного доступа к файловой системе, секретам и сети. Требуются:

- Список разрешённых директорий.
- Sandbox для сборок и тестов.
- Журнал действий.
- Контроль затрат и времени.
- Возможность остановки долгих операций.

Конкретный локальный транспорт, механизм разрешений, изоляция процессов, политика доступа к секретам и сети, лимиты и механизм остановки пока не выбраны. Локальность API сама по себе не подтверждает изоляцию. Эффективность ограничений должна быть проверена при реализации.

## AI Game Tester

Требуются детерминированные сценарии ввода и проверки коллизий, прохождения уровней, поведения транспорта и save/load; сбор логов и скриншотов, поиск регрессий.

Не обещать, что AI гарантирует отсутствие ошибок. Отчёты должны указывать выполненные сценарии, результаты и ограничения проверки.

Предложения оптимизации проверяются на изменения поведения и визуальные отличия. Исходные пользовательские ресурсы сохраняются при генерации оптимизированных копий.

Будущая работа AI с C# исходниками не означает доверенное или автоматически безопасное исполнение сгенерированного кода. Проектные скрипты должны рассматриваться как обычный код с правами процесса до появления отдельно проверенной изоляции.

### Разрешение на запуск C# в Play Mode (04.11, политика)

Перед будущей загрузкой скриптов Play Mode Editor должен собрать все enabled `ScriptBehavior` текущей Scene, разрешить каждую привязку и подтвердить актуальные build hashes. До загрузки CLR/assembly пользовательский диалог показывает точный набор: project и Scene, AssetId, source path, managed type, build fingerprint и идентификатор/хеш output generation. Подтверждение действует только на этот набор и одну Play-сессию; Stop или повторный Play требует нового согласия. Смена project/Scene, состава скриптов, manifest, source, assembly или runtimeconfig hash до загрузки инвалидирует его. После прямого подтверждения Editor повторно разрешает весь набор и сравнивает его с показанным snapshot непосредственно перед host load; любое расхождение прекращает запуск. Missing/stale/invalid binding и отмена блокируют весь script-set до lifecycle callbacks; ошибки не допускают частичного вызова компонентов. Hot reload в этом контракте отсутствует: изменения на диске относятся к следующему Play.

Согласие не сохраняется как повторно используемое доверие в project manifest, scene или user settings. Codex, AI Editor API, CLI, build success и тестовый отчёт не могут самостоятельно его выдать. AI может запросить Play-проверку, после чего ожидать прямого действия пользователя в Editor. Editor gate реализован в 04.12; 04.13 подключает его к Play: перед каждой уникальной host-загрузкой runtime повторно сверяет точный snapshot, затем запускает lifecycle enabled ScriptBehavior. Это UX/accidental-execution policy, не security sandbox: загруженный C# получает права текущего процесса, включая доступные ОС API/файлы/сеть. Низкоуровневая C++ функция `CSharpScriptHost::loadScriptAsset` сама не содержит permission gate и предназначена для доверенного использования и тестов.

## Будущая проверка реализации

При реализации соответствующих подэтапов проверить пайплайн команд, отклонение недопустимых схем и неразрешённых действий, подтверждение рискованных операций, ограничения директорий/секретов/сети, изоляцию сборок и тестов, аудит, лимиты и остановку. Проверить запуск игры и редактора без AI-интеграции и повторяемость детерминированных сценариев тестера.

Зависимости: Typed Command API, схемы, модель проекта/сцены, транзакции, диагностика и тестовая инфраструктура. Конкретные SDK, модели, протоколы и версии не выбраны. Исполняемых тестов и подтверждений безопасности пока нет.

### C# worker security boundary prototype (04.19)

The standalone Windows metadata-validator currently has no AI or Editor caller. Any later caller must preserve its bounded protocol and AppContainer policy; an AI request cannot grant capabilities, widen project paths, or bypass consent. Integration and project-root path validation are not implemented. The metadata reader is not certified for hostile PE, and the existing C# runtime host is still in-process/trusted-code-only. See [D084](DECISIONS.md#d084--windows-c-metadata-validator-worker-prototype-0419) and [04.19 report](reports/04.19-csharp-metadata-validator-worker.md).
