# Графический редактор и UX

Статус: требования пользователя из раздела 05. Документ не определяет окончательный макет интерфейса. На 02.3 есть первые панели Scene View (структурное дерево), Hierarchy и Inspector для schema properties сущности; остальные области и рабочие пространства не реализованы.

## Основные области

Scene View, Game View, Hierarchy, Inspector, Asset Browser, Console/Diagnostics, Project Settings, Timeline, Visual Logic, Profiler.

## Рабочие пространства

Мир, Объекты, UI, Анимация, Логика, Материалы, Камеры, Сохранения, Тестирование, Сборка.

Инструменты организуются по рабочим пространствам согласно P10 в [продуктовых требованиях](PRODUCT_REQUIREMENTS.md). Конкретный состав и расположение областей в каждом пространстве пока не определены.

## Основные операции

- Создание и открытие проекта и сцены, сохранение.
- Поиск, фильтры, drag-and-drop и multi-select.
- Gizmos для перемещения, вращения и масштаба.
- Сетка и привязка.

## Встроенный редактор кода C# (P15)

Editor должен включать отдельную Code workspace/window для ручного редактирования игровых скриптов на C#. В контексте требований это текстовый редактор исходного кода внутри Editor, а не произвольная командная оболочка ОС.

Минимальные критерии будущей реализации: создавать/открывать/сохранять `.cs` файлы проекта; корректно обрабатывать UTF-8 и несохранённые изменения; показывать ошибки и предупреждения компиляции с переходом к строке; компилировать скрипты текущего проекта и сообщать диагностируемый результат. Скрипт должен подключаться к объекту/сцене через явную схему и документированный runtime API, с Inspector-свойствами только для публично поддержанных типов.

Подэтап 04.15 добавил базовую Windows workspace на существующем Dear ImGui: файловый список `Scripts/**/*.cs`, создание/открытие/атомарное UTF-8 сохранение, dirty prompt, явный запуск локального build pipeline и compiler diagnostics с переходом к source line. Открытие ограничено `.cs` внутри `Scripts` и 4 MiB на файл. Платформенная оценка host/SDK и лицензий остаётся открытой; syntax highlighting, LSP, debugger, refactoring и sandbox отсутствуют. См. [C# scripting API](CSHARP_SCRIPTING_API.md) и [отчёт 04.15](reports/04.15-csharp-code-workspace.md).

Подэтап 04.16 добавил в C# Code workspace сворачиваемую форму Build settings для `.astro/csharp-build.json`: закреплённый SDK 10.0.x, фиксированный `net10.0`, имя сборки и список bindings из `Scripts/**/*.cs`. Изменения сохраняются только по кнопке. Некорректный существующий манифест нельзя заменить без подтверждения. Поддерживаются только SDK/framework текущего prototype; см. [отчёт 04.16](reports/04.16-csharp-build-manifest-editor.md).

Подэтап 04.17 уточнил сообщения в Project → C# scripts: они различают отсутствующую регистрацию, несовпадающий managed type, устаревший source hash и output другой сборки. **Register current C# build** синхронизирует выбранные manifest bindings и сохраняет AssetId для тех же исходников. Это сравнение manifest/build/index; CLR тип не загружается автоматически и проверяется только при явном одобренном Play.

Отдельный от текстового редактора source-code, в 04.14 Inspector получил раннее authoring существующих `ScriptBehavior`: выбор актуального registered binding проекта, создание выключенного компонента, toggle enabled и удаление с Undo/Redo. Для включения требуется свежая C# build registration; код скрипта здесь не редактируется и не компилируется. См. [C# API](CSHARP_SCRIPTING_API.md) и [04.14 report](reports/04.14-scriptbehavior-editor-authoring.md).

## Команды и сохранность изменений

Редактирование свойства через GUI и через Command API должно быть эквивалентным. GUI использует единый механизм команд согласно [архитектуре](ARCHITECTURE.md).

Требуются Undo/Redo, история изменений, обработка конфликтов и несохранённых правок. Конкретные сценарии разрешения конфликтов и предупреждения о несохранённых изменениях подлежат дальнейшему проектированию.

## Материалы

Требуются PBR-параметры: цвет, металл, шероховатость, прозрачность и эмиссия, а также замена текстур. Узловой редактор шейдеров относится к более поздним возможностям.

## Камеры

Режимы: First Person, Third Person, Isometric, Top-Down, Platformer, Strategy.

Возможности: следование, сглаживание, границы, зум и переключение. Кат-сцены относятся к более поздним возможностям.

## UI

Требуются визуальные панели, кнопки, HUD, меню, адаптивная вёрстка, темы, навигация с клавиатуры и геймпада, локализация и масштабирование.

## Зависимости и проверка реализации

Реализация опирается на механизм свойств, Typed Command API, Undo/Redo, модель сцен и ресурсов из архитектурных требований. Выбор конкретных библиотек остаётся предварительным согласно [TECH_STACK.md](TECH_STACK.md).

При реализации соответствующих подэтапов необходимо проверять эквивалентность GUI и команд, Undo/Redo и сохранность несохранённых правок. GUI Inspector применяет Name через `entity.set_property` Command API; интеграционные и smoke-тесты это проверяют. Полноценный редактор, визуальные эталоны и ручная UX-проверка мышью пока отсутствуют.

## Камеры (04.3)

В 04.3 реализован programmatic runtime CameraRig API для pose/follow и параметров. Это не renderer и не визуально проверенная камера. Для изображения необходима последующая интеграция с Game View/runtime renderer; требования к camera modes описаны выше.
