# Продуктовые требования и принципы

## Цель продукта

AstroEngine — универсальный модульный движок и графический редактор для создания 2D- и 3D-игр разных жанров. Долгосрочный ориентир по широте продукта — общие игровые движки уровня Unity, Godot, Unreal Engine и CryEngine; это направление развития, а не заявление о текущем паритете функций.

Ключевое отличие продукта — создание и изменение проекта с помощью ИИ как одного из основных авторских рабочих процессов. Разработчик должен иметь возможность поручить ИИ изучить проект, спланировать изменение, показать проверяемый diff, применить его через те же типизированные операции, что использует GUI, запустить проверки и получить отчёт. ИИ не редактирует Scene/проект в обход Command API и ограничений доступа.

GUI, визуальная логика, AI-команды и программные расширения — согласованные способы управлять одной моделью проекта. Необязательное подключение конкретного ИИ-провайдера не должно требоваться для запуска редактора, сборки или готовой игры. ИИ является ключевым путём создания игры, но движок не привязывается к одному поставщику и сохраняет работу без сети.

Puzzle — текущий ранний игровой пример и сквозной проверочный сценарий для Editor, runtime, кампаний и сохранений; он не определяет жанровые границы продукта. Новые жанры, полноценный 3D и платформы добавляются постепенно, после проверенной основы и с честными критериями готовности. Заявленная универсальность — целевая архитектура, а не текущая реализация.

## Продуктовые инварианты

- Общие действия над проектом проходят через общий типизированный контракт; GUI и ИИ не получают отдельные несовместимые модели данных.
- Для изменений, инициированных ИИ, проектируются план, валидация схем/разрешений, diff, подтверждение рискованных операций, транзакция или обозначенная необратимость, тесты и аудит.
- Редактор, runtime и build/export разделены; игровая сборка не включает редактор или AI adapter без явного запроса.
- Любое расширение универсальности доказывается работающим примером и тестами. Наличие интеграции с ИИ не считается гарантией корректности сгенерированных изменений.

## Требования

- **P01.** Одинаковый результат действий через мышь/GUI, визуальную логику и AI-команды.
- **P02.** Модульность: необязательные подсистемы не запускаются и не включаются в сборку без нужды.
- **P03.** Простая модель: сцена → сущность → компоненты → свойства; минимум специальных классов.
- **P04.** Единый механизм свойств: типы, диапазоны, значения по умолчанию, инспектор, анимация, сериализация, команды, валидация, доступ для AI.
- **P05.** Undo/Redo и транзакции для редакторских операций.
- **P06.** Стабильные ID объектов, сцен, ресурсов, префабов и сохраняемых экземпляров.
- **P07.** Исходники ресурсов неизменны; производные ресурсы кэшируются и пересоздаются.
- **P08.** Сериализация с версиями схем, миграциями и диагностикой неизвестных компонентов.
- **P09.** Предпросмотр AI-изменений, подтверждение, контрольные точки, откат.
- **P10.** Инструменты редактора по рабочим пространствам, а не десятки панелей одновременно.
- **P11.** Проект собирается воспроизводимо, по возможности без скрытых глобальных зависимостей.
- **P12.** Отдельные Editor, Runtime и Build/Export: готовая игра не включает редактор.
- **P13.** Доступность инструментов без ручного написания кода; расширяемость программированием.
- **P14.** Проверяемая функциональность важнее количества обещанных возможностей.
- **P15. Редактор кода C#.** В составе Editor должна быть отдельная встроенная рабочая область/окно для ручного создания и редактирования игровых скриптов на C#. Скрипты должны сохраняться в проекте, компилироваться с диагностикой и подключаться к runtime через документированный API движка. Перед первым фактическим исполнением пользователь должен явно подтвердить конкретный набор скриптов и точную сборку для текущей Play-сессии; AI, проектный файл или факт успешной сборки не могут автоматически выдать это согласие. Подтверждение не считается sandbox и не ограничивает права in-process кода. Конкретные editor flow, compiler/runtime host, модель сборки и платформенные ограничения требуют оценки; P15 фиксирует цель и не означает реализованную поддержку C#.

Кодовые расширения и no-code/AI-команды дополняют друг друга. C# скрипты не должны обходить границы Engine/Scene API; изменения файлов, инициированные AI, подлежат diff, проверкам разрешений, подтверждению по правилам AI-интеграции и сборочным/регрессионным тестам.
