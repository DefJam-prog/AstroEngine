# 04.11 — C# Play approval policy

**Status:** design substage complete. No permission gate, UI, or RuntimeSession lifecycle was implemented.

## Decision

Before Editor Play loads any enabled `ScriptBehavior`, it must request direct user consent for the exact set in the current project and Scene. The confirmation lists each AssetId, source path, managed type, build fingerprint, and output hashes. The consent is temporary and valid for one Play session only; it is not saved as reusable project/user trust.

After confirmation, the Editor re-resolves all bindings and rechecks the manifest, source/build identity and output hashes against the displayed snapshot immediately before loading. Any changed state aborts the whole set. Cancel, missing/stale/invalid records, or host-load failure must not trigger lifecycle callbacks for a partial set. Stop, another Play, switching project/Scene, changing the enabled script set, or changing the approved build invalidates consent. Hot reload is outside this policy.

Codex/AI, CLI commands, a successful build, and a prior test result cannot grant consent. An AI-requested Play check waits for a direct user action in Editor. A future local audit may record that action, but it must not persist reusable trust.

This is an explicit consent/accidental-execution policy, **not a sandbox**. Once loaded, C# runs inside the process with the user's available OS, file, and network privileges. The current low-level `CSharpScriptHost::loadScriptAsset` still has no gate and remains a trusted C++ API used directly by integration tests; the future Editor Play flow must enforce the policy before calling it.

## Future acceptance checks

The implementation substage must verify no prompt/load when no enabled scripts exist; the dialog lists the complete exact set; Cancel invokes no script; confirmation is bound to one Play only; stale or changed state aborts all callbacks; disabled behaviors are excluded; Stop/restart requests consent again; and AI/CLI cannot auto-confirm. Any test-only approval route must exist only in test targets/fixtures and have no production auto-approval path.

## Recommended next substage

Implement and test the Editor consent gate before connecting ScriptBehavior callbacks to RuntimeSession. Keep the host's in-process limitations visible and do not present this gate as a security sandbox.
