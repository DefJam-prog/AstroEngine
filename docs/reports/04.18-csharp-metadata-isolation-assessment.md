## Findings

`System.Reflection.Metadata.dll` exists in the local .NET reference/runtime packs. `System.Reflection.MetadataLoadContext.dll` was found only under SDK-private tool directories, not the shared runtime pack. Binding a project to an SDK-private DLL path would be fragile and is not recommended. No external package was added or selected in this assessment.

Microsoft documents `MetadataLoadContext` as metadata inspection that does not execute inspected user code, while advising use of `GetCustomAttributesData()` rather than executing attribute constructors. That property is useful for type/signature inspection but is not a parser-security guarantee. Microsoft's `MetadataReader` documentation warns that the low-level API is not designed for untrusted input. `AssemblyLoadContext` is explicitly not a security boundary: code in the process has the process's privileges.

Recommended Windows design: a separate validator worker process under AppContainer with only narrowly scoped read access to approved build/reference inputs, a private temporary output location, and no network/profile/secrets access. Bound request size, metadata counts/depth where supported, and wall-clock time. Place the worker in a Job Object to cap resources and terminate its process tree. A Job Object is supplemental resource control, not a filesystem/network sandbox. The Editor receives a small versioned diagnostic response and never maps the project DLL into its own CLR process.

For future execution of untrusted gameplay scripts, use a separate runtime worker with a narrow versioned IPC contract and OS policy. Do not send raw Editor function pointers or expose the complete document/filesystem API. The existing in-process ABI v1 remains usable for trusted local prototypes; no migration or backward-incompatible API change is made here.
