# 04.19 — Windows C# metadata-validator worker prototype

## Scope

Implemented only the 04.19 Windows x64 worker prototype. It is a standalone CLI and is not connected to the Editor Project panel, Play flow, or AI API. The existing C# host ABI and project diagnostics are unchanged.

## Implementation

- Added `tools/csharp/metadata-validator`, targeting .NET 10 and using `System.Reflection.Metadata` from the shared framework; no NuGet dependency or network restore is required.
- The CLI stages one selected managed assembly (maximum 64 MiB), starts a separate worker under a temporary AppContainer with zero declared capabilities, and gives its SID ACL access only to the temporary worker/runtime/input/output tree. The process receives a restricted environment allowlist; user-defined environment variables are not inherited.
- The worker uses a versioned JSON request/response bounded to 16/32 KiB. It finds the exact requested managed type and checks `OnCreate`, `FixedUpdate`, and `OnDestroy` for the current ABI v1 `public static int (IntPtr, int)` signature and `UnmanagedCallersOnlyAttribute`. It reads metadata directly and does not load the inspected assembly or instantiate custom attributes.
- A Job Object applies a 512 MiB process-memory limit and kill-on-close. The parent enforces a 15 second operation timeout, validates the response schema/size, then removes the temporary profile and staging tree.
- Added a dependency-free C# fixture with a Unicode namespace, valid and invalid method signatures, and a module initializer that throws if the assembly is initialized. Added a PowerShell integration test and CTest registration for C# Release builds.

## Verification

Focused integration script:

```powershell
$repo = (Get-Location).Path
pwsh -NoProfile -File tests/integration/runtime/CSharpMetadataValidatorTests.ps1 `
  -RepositoryRoot $repo `
  -DotnetRoot (Join-Path $repo 'build/04.5-dotnet-sdk') `
  -ValidatorProject (Join-Path $repo 'tools/csharp/metadata-validator/AstroEngine.CSharpMetadataValidator.csproj') `
  -WorkParent (Join-Path $repo 'build/04.19-focused-tests')
```

It passed and covered a valid binding, Unicode managed type name, invalid signature, unknown type, malformed PE, >64 MiB PE rejection, no module initializer execution, denied read of an outside sentinel, denied loopback TCP access, and timed worker termination.

Full regression:

```powershell
cmake --build build/04.8-debug-clean
ctest --test-dir build/04.8-debug-clean --output-on-failure
cmake --build build/04.8-release-clean
ctest --test-dir build/04.8-release-clean --output-on-failure
```

- Debug: **45/45 passed**, 7.76 seconds.
- Release with C# host: **48/48 passed**, 47.51 seconds. The new `runtime.csharp_metadata_validator.integration` passed in 20.18 seconds.
- Logs: `build/04.19-debug-{build,ctest}.log`, `build/04.19-release-{build,ctest}.log`.
- The worker project itself built with .NET SDK 10.0.404, zero warnings and zero errors.

## Limits and risks

- Microsoft documents `MetadataReader`/`MetadataReaderProvider` as not designed for untrusted input. AppContainer deny checks and resource limits passed on this one Windows machine, but do not certify every Windows/runtime attack surface. The prototype must not be advertised as safe arbitrary hostile-PE processing.
- Windows x64 and a local .NET 10 runtime are required. There is no macOS/Linux worker.
- The caller currently accepts an assembly path directly; project-root authorization belongs to a later Editor integration substage. The tool is not called automatically.
- This checks the current three-method ABI binding only. It does not resolve all runtime load errors, validate source/build hashes, execute scripts, or inspect every component/API constraint.
- The runtime and worker are copied to a fresh temporary tree for each request, so inspection has significant startup and I/O overhead. No performance optimization or persistent cache was added.
- The in-process Play host remains trusted-code-only and unchanged.

The low-level metadata parser warning is documented in [Microsoft's `System.Reflection.Metadata` reference](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata?view=net-10.0); process isolation relies on [AppContainer security capabilities](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-security_capabilities) and [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Decision D084 records the adopted prototype boundary. The next recommended substage is 04.20, Project panel diagnostics integration with explicit project-root path validation; it has not been started.
