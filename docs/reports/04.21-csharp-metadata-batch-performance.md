# Подэтап 04.21 — пакетная C# metadata-проверка и профиль

Дата: 2026-11-15  
Платформа: Windows x64, Windows 10.0.26300, MSVC 14.44, .NET SDK 10.0.404.  
Область: профиль процесса/стейджинга metadata-worker и улучшение batch UX; runtime ABI, sandbox, ACL и структура staging не менялись.

## Исходный baseline

До кода повторно прошли полные проверки: Debug CTest **46/46** (10.77 с), Release+C# CTest **49/49** (61.30 с). Для benchmark использован локальный .NET runtime из `build/04.5-dotnet-sdk`.

Создан временный offline C# проект с 128 public static managed types; у каждого три `UnmanagedCallersOnly` ABI v1 entry point. Сборка сгенерирована только в игнорируемом `build`.

- Одна проверка одного типа: **1.67 с** в первом холодном измерении.
- Пакет из 16 типов: **1.33–2.17 с** на один worker-запуск в измеренных повторах; metadata-ответ около **2,275 байт**.
- Один 64-type сценарий через прежние четыре последовательных 16-type worker сессии: **5.478 с** суммарно.
- Эти времена включают запуск CLI, runtime staging/copy, создание AppContainer и metadata inspection. Инструментального CPU profiler пофункционно не применялось; разница масштабирования и время на пакет указывают, что повторное создание/копирование доминирует над быстрым metadata scan на этой сборке.

В дополнение проверен существующий `AstroEngine.CSharpSample.SceneMotion` из C# runtime sample: три изолированных one-type проверки заняли **1.064 / 1.016 / 0.938 с**, median **1.016 с**. У sample всего один registered-like type, поэтому он показывает стартовую цену для малого проекта, но не представляет большой проект.

## Изменения

- Лимит одного `inspect-many` worker поднят с 16 до 64 managed types. Ограничение суммарных имён — **8 KiB UTF-8 bytes**; сериализация request оставлена корректно bounded в пределах **16 KiB**. Для Unicode применён UTF-8 friendly JSON encoder и проверяется размер UTF-8, а не число UTF-16 code units.
- Существующие ограничения worker сохранены: response до **32 KiB**, assembly до **64 MiB**, AppContainer без capabilities, staged ACL, Job Object 512 MiB и 15-секундный worker deadline. Editor runner timeout остаётся 90 секунд на каждый отдельный worker process. Runtime и worker по-прежнему копируются в новый temporary staging для каждого batch.
- Добавлен проверяемый splitter Editor-плана: не больше 64 типов на пакет, 8 KiB суммарных UTF-8 type-name bytes, максимум 256 типов на план. При больших планах вывод содержит отдельные JSON responses, ограничен **128 KiB** и помечает усечение; панель показывает число запрошенных типов и worker-пакетов.
- Shared/persistent runtime cache не добавлен: увеличение batch уже убирает основную повторную стоимость, не требуя долговременных каталогов, повторного использования AppContainer identity или постоянных ACL.

## Результат benchmark после изменения

Включённый benchmark runner генерирует временную сборку из 256 ABI-shaped типов и повторяет полный CLI/worker путь три раза на каждый размер. Полученные median total wall times:

| Запрошено типов | Worker batches | Median total | Min–max |
| ---: | ---: | ---: | ---: |
| 1 | 1 | 1.214 с | 1.192–1.620 с |
| 16 | 1 | 1.365 с | 1.351–1.468 с |
| 64 | 1 | 1.346 с | 1.280–1.367 с |
| 128 | 2 | 2.568 с | 2.447–2.809 с |
| 256 | 4 | 5.525 с | 4.299–5.661 с |

Для 64 типов новый median **1.346 с** примерно в **4.1 раза** быстрее прежнего измеренного последовательного случая **5.478 с** (около 75% меньше wall time). Ответ каждого 64-type worker — **8,659 байт**. При четырёх batch-ответах 256-type JSON составляет около 34.6 KiB, поэтому старый общий 32 KiB Editor cap мог бы обрезать валидные результаты; новый 128 KiB cap покрывает измеренную максимальную конфигурацию и оставляет место для variance.

Это synthetic benchmark одного Windows компьютера, не репрезентативная сборка с внешними зависимостями/многочисленными исходниками и не гарантия времени на других устройствах. Реальный sample проверен отдельно; реальный проект пользователя не предоставлялся.

## Остаточные ограничения и следующий шаг

AppContainer и parser security posture остались прежними: это ограничение риска, не сертификация безопасности недоверенных PE. Проверка работает только на Windows x64; в-process Play host остаётся trusted-code-only. Списки больше 64 всё ещё платят примерно за отдельный runtime staging для каждого worker. Полный persistent cache не нужен по текущему synthetic measurement; сначала следует проверить задержку и UX на реальном проекте пользователя.

Следующий рекомендуемый подэтап — **04.22:** измерить metadata-check на реальном проекте и проверить прокрутку/читаемость отчёта около 128 KiB, не меняя sandbox или ABI.
