# Отчёт 04.5 — C# runtime technical prototype

Дата завершения: 2026-11-14. Подэтап выполнен в согласованных пределах: собран optional Windows x64 native host на `nethost`/`hostfxr`, managed C# sample запускается из fixed-step `RuntimeSession`, regression suite проходит. Результат — технический прототип, не production runtime и не редактор кода.

## Объём

- Выбрать исполняемый hosting путь для технического прототипа и проверить нативный C++ -> managed C# вызов.
- Подключить sample к изолированной runtime-копии сцены и проверить поведение Play/Stop.
- Не реализовывать Code workspace, общий C# bindings API, ScriptBehavior, hot reload, sandbox или мобильную поддержку.

## Реализация

- `ASTRO_BUILD_CSHARP_RUNTIME` — CMake option, OFF по умолчанию. При ON требует Windows x64 MSVC и заданный `ASTRO_DOTNET_ROOT` с SDK host pack.
- `astro_runtime_csharp` использует `get_hostfxr_path`, загружает hostfxr из заданного SDK root, инициализирует framework-dependent component по runtimeconfig и получает function pointer для `UnmanagedCallersOnly` метода.
- Ошибки аргументов, отсутствующих файлов, ошибок hostfxr, загрузки entry point и ненулевого кода скрипта возвращаются через `astro::core::Result`; payload ограничен размером `int32_t` ABI.
- Dependency-free sample `SceneMotion` принимает маленький ABI payload (fixed delta, X position), проверяет размер и конечный положительный timestep, двигает позицию на fixed delta и возвращает диагностический код.
- C++ integration adapter вызывает его из `RuntimeSession` fixed-step callback и переносит полученное значение в Transform runtime-копии. В сам C# не передаётся Scene API или произвольный доступ к движковым объектам.
- `.NET` host запускает код in-process с правами процесса AstroEngine. Это не sandbox; недоверенные скрипты запускать нельзя.

## Команды и фактические результаты

Использованы Visual Studio 2022 x64 Build Tools и Ninja. PowerShell-команды:

```powershell
$env:DOTNET_CLI_TELEMETRY_OPTOUT = '1'
$sdk = (Resolve-Path 'build/04.5-dotnet-sdk').Path
cmake -S . -B build/04.5-csharp-host -G Ninja `
  -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON `
  -DASTRO_BUILD_CSHARP_RUNTIME=ON -DASTRO_DOTNET_ROOT="$sdk"
cmake --build build/04.5-csharp-host --target astro_csharp_runtime_integration_tests --parallel 4
ctest --test-dir build/04.5-csharp-host -R runtime.csharp_host.integration --output-on-failure
cmake --build build/04.5-csharp-host --parallel 4
ctest --test-dir build/04.5-csharp-host --output-on-failure -j 4
cmake --build build/stack-spike --parallel 4
ctest --test-dir build/stack-spike --output-on-failure -j 4
```

Результаты:

- Release CMake configure — успешно.
- Target `astro_csharp_runtime_integration_tests`, включая C++ host и C# sample — успешно.
- Focused `runtime.csharp_host.integration` — **1/1 passed**, 0.19 s на первом успешном запуске; после полной пересборки — **1/1 passed**, 0.14 s.
- Полный Release CTest с C# option — **36/36 passed**, 0.87 s при финальном повторе (первый полный прогон после полной сборки занял 12.88 s).
- Существующая `build/stack-spike` сборка — успешно; CTest **42/42 passed**, 7.53 s.
- SDK build log сохранил `Build succeeded`, 0 warnings, 0 errors для managed sample. Общая C++ сборка выводит существующие `/EHsc` и другие предупреждения некоторых targets; они не блокировали сборки и этим подэтапом не исправлялись.
- Первый focused запуск завершился .NET `Invalid Program`, потому что host запрашивал обычный managed delegate для `[UnmanagedCallersOnly]`. Параметр получения delegate исправлен на `UNMANAGEDCALLERSONLY_METHOD`; повторный focused и оба полных набора прошли.

Пример конфигурации выше предполагает, что `cl.exe` доступен из Developer PowerShell for VS 2022 x64. В обычном PowerShell можно обернуть вызовы CMake в `cmd /c` с `vcvars64.bat`, например:

```powershell
cmd /c 'call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat" && cmake --build build/04.5-csharp-host --parallel 4'
```

## Ограничения и следующий рекомендуемый подэтап

- Прототип поддерживает только Windows x64 MSVC и требует framework-dependent .NET runtime при запуске; runtime packaging, размер поставки и версия production target не оценены.
- Изменение сцены проксируется тестовым payload; стабильный, версионированный и валидируемый Script API ещё не определён. `ScriptBehavior`, scripting lifecycle, сериализация bindings и editor diagnostics отсутствуют.
- Crash/memory boundary, permissions, sandbox, AI approval flow, hot reload, multi-script lifecycle, threading, mobile deployment/AOT и license/notice review не проверялись.
- Нативная зависимость включается только при явном `ASTRO_BUILD_CSHARP_RUNTIME=ON`; обычные конфигурации не требуют .NET SDK.

Рекомендуемый следующий подэтап: дизайн и проверка стабильного versioned C#-to-engine API/ScriptBehavior на Windows, включая scene/property validation и тесты ошибок; до реализации встроенного Code workspace отдельно определить доверенную модель скриптов. **04.6 не начат.**
