# 04.9 — project-local C# build and stale diagnostics

**Status:** complete. Supplemental C# tooling step; no RuntimeSession lifecycle or Editor UI work was started.

## What changed

- Added `tools/csharp/build-project.ps1` and `AstroCSharpProjectBuild.psm1`. The CLI uses PowerShell 7 and the SDK path supplied by the project/developer; the manifest pins the exact .NET 10.0.x SDK version and `net10.0` target framework.
- Project configuration lives at `.astro/csharp-build.json` with schema version 1 and the assembly simple name. Unknown/missing fields, unsupported framework/SDK, unsafe names, missing source files and reparse-point paths are rejected.
- The builder compiles regular `Scripts/**/*.cs` files only. It stages a hash-checked copy of those inputs under ignored `Library/Scripts`, generates an SDK-style class-library project, and restores with `tools/csharp/NuGet.Config`, whose package source list is empty.
- The compiler uses deterministic/CI build properties. A successful build writes DLL and runtimeconfig into a new generation directory under `Library/Scripts/<assemblyName>/`; previous generations are not overwritten or automatically deleted. `Library/Scripts/build-state.json` stores the input fingerprint, SDK/framework, relative output paths and SHA-256 hashes. State publication uses a sibling temporary and replacement after both outputs exist.
- `-Check` exits 0 for current inputs/outputs, 3 for stale or missing output, and 2 for invalid project/tool configuration. Build/restore failure exits 1 and leaves the previous successful build-state untouched. The CLI does not register an AssetId or execute the script.
- CMake registers `runtime.csharp_project_build.integration` for the optional C# configuration when PowerShell 7 is available. It tests the real local SDK, offline compilation, identical DLL bytes from two project paths (one containing Cyrillic), UTF-8 CLI output/path parsing, fresh/stale CLI exit codes, invalid UTF-8 rejection, source update to a new generation, preserving the prior state after a compiler error, and detecting output tampering.

## Limits

- This prototype targets .NET 10.0.x/net10.0 and does not settle the production SDK/runtime choice or support packages. NuGet sources are intentionally disabled; scripts cannot declare external package dependencies in this step.
- Build-state is project-local derived state, not an AssetRegistry entry. The editor/runtime still need to choose managed type, call `registerScript`, and report diagnostics through a project UX.
- Generations and failed staging folders are retained under ignored `Library/Scripts`; no automatic cache pruning was added.
- C# is compiled as the current user and later host-loaded in-process. This is not a sandbox. It does not connect ScriptBehavior to RuntimeSession lifecycle, implement hot reload, or export/package the SDK/runtime.
- The integration test requires the local pinned SDK and PowerShell 7. CMake omits it when `pwsh` is unavailable.

## Recommended next substage

After manual confirmation, connect the successful build-state to AssetRegistry registration and project diagnostics, including managed-type selection/validation and a stale status visible to project tools. Runtime lifecycle wiring should remain a separate subsequent substage and needs an explicit permission policy for executing user scripts.
