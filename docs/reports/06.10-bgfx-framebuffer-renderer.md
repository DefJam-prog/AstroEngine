# Direct bgfx framebuffer rendering for Scene/Game View

Date: 2026-11-13

## Implementation

- Scene View and Game View now use bgfx view IDs 1 and 2. Their independent BGRA8 framebuffer attachments are rendered before the existing ImGui backbuffer view 0.
- `astro_scene_render2d` still composes hierarchical affine SpriteRenderer corners into backend-neutral Canvas2D commands. The editor adapter maps those corners to the existing ImGui-compatible position/UV/color vertex layout, allocates bgfx transient vertex/index buffers, and submits adjacent same-texture sprites together.
- The framebuffer texture is displayed through ImGui, with UV orientation selected from bgfx caps. Resize recreates each attachment. Texture decode/loading continues through the Editor's existing AssetRegistry/WIC-to-bgfx cache.
- Editor no longer links the SDL software renderer or SDL WIC texture-cache adapters. Those remain available to the standalone runtime/playground.
- No GPU readback or external dependency was added.

## Comparison method

Used `astro_editor --benchmark` on both revisions with the same synthetic 1, 100 and 1000 SpriteRenderer scenes, one cached 1x1 PNG, grid transforms and 960x540 views. Each case uses 8 warm-up and 40 measured frames. The prior CPU baseline measured Canvas preparation, SDL rasterization and bgfx full-frame upload submission. The new path measures Canvas/vertex preparation and bgfx draw submission. Asynchronous bgfx GPU frame timer samples cover both offscreen views when provided by the driver. CPU totals exclude UI composition and vsync. This is a local Windows x64/MSVC Debug run on the D3D11 backend, not a release target budget.

## Results

| Sprites | CPU Scene p50 / p95 | CPU Game p50 / p95 | Paired GPU frame p50 / p95 |
|---:|---:|---:|---:|
| 1 | 0.030 / 0.041 ms | 0.012 / 0.015 ms | 0.044 / 0.050 ms* |
| 100 | 0.424 / 0.618 ms | 0.416 / 0.617 ms | 0.025 / 0.041 ms* |
| 1000 | 4.809 / 5.789 ms | 4.782 / 5.618 ms | 0.074 / 0.135 ms |

*GPU timestamp samples available after warm-up: 36 for one sprite, 37 for 100, and 40 for 1000. GPU times are asynchronous bgfx whole-frame timestamps around both offscreen views; timer noise/scheduling explains why the one-sprite sample is not a monotonic cost curve.

At 1000 sprites, the paired CPU p50 sum is 9.591 ms versus the previous bridge's 15.373 ms, a 37.6% reduction. Adding each pane's p95 as a conservative estimate gives 11.408 ms versus 18.271 ms previously. The views now upload **0 framebuffer bytes from host memory**. Two 1000-sprite views copy 184,000 bytes of transient vertex/index data into bgfx buffers; the GPU writes their framebuffer attachments internally. For 100 sprites, the summed CPU p50 falls from 3.325 ms to 0.840 ms.

## Limits

- The benchmark is synthetic and repeats one 1x1 cached texture; unique texture count, large image sampling, animation, editor overlays and full UI composition are not represented.
- CPU preparation of the scene and transient vertices dominates at 1000 sprites (~5.3–5.6 ms per view). The next optimization target is avoiding repeated per-entity hierarchy traversal and reducing temporary allocations.
- The smoke validates draw/view lifetime and both frame outputs, but there is no image golden for rotation/alpha/orientation across multiple graphics APIs. Manual visual walkthrough was not completed. The actual configured backend here is D3D11 only.
- Game View still has an empty fixed-step callback; this work changes presentation only and does not add gameplay execution.
