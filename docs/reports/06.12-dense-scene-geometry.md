# 06.12 — Dense Scene/Game View geometry profiling and optimization

## Scope

Profile and accelerate Scene/Game View CPU preparation for dense sprite scenes, then build and benchmark the full Editor in Release. No next engine substage, new dependency, Scene API change or scene format change was started.

## Baseline and profile

Windows 11 x64, MSVC 2022, D3D11. Before code changes the Debug Editor built, the full optional CTest suite passed **37/37**, and the 960×540 benchmark was run for 1/100/1000/5000/10000 sprites. Baseline 10k CPU p50 was 145.079 ms Scene and 144.091 ms Game in the uninstrumented run (`build/06.12-baseline-debug-benchmark.log`).

Stage timing was then added to the benchmark. Before optimization, at 10k sprites:

| View | Scene composition | Camera bounds | Vertex geometry | Transient alloc/copy | bgfx submit | Total CPU p50 |
|---|---:|---:|---:|---:|---:|---:|
| Scene | 136.750 ms | 0.326 ms | 4.922 ms | 0.088 ms | 0.187 ms | 142.218 ms |
| Game | 135.800 ms | 0.334 ms | 4.931 ms | 0.082 ms | 0.184 ms | 141.326 ms |

The dominant cost was `Scene::transform(id)` doing a linear `Scene::find()` for every sprite; repeated parent resolution was also linear. A flat N-sprite scene therefore performed O(N²) entity lookup work. Profiling output is retained in `build/06.12-profile-stages.log`.

## Implementation

`engine/render2d/SceneSprites.cpp` now builds an EntityId-to-vector-index lookup once per composition. A vector-backed cache composes each parent affine transform once and reuses it for descendants. The cache is local to the function call, so scene edits cannot leave stale world transforms in subsequent frames. Cycle, missing parent, missing Transform and finite-value checks are retained.

For transforms with exactly zero Z rotation, the local affine matrix skips sin/cos. Axis-aligned matrix column lengths use `abs()` when the off-axis coefficient is exactly zero, keeping the general `hypot()`/`atan2()` path for rotated and sheared transforms. Sprite records are moved into Canvas2D after the existing all-or-nothing validation.

`editor/main.cpp` benchmark now separately reports composition, camera-bounds scan, vertex/index generation, transient allocation/copy and bgfx submission CPU p50. The renderer and Scene public API are unchanged.

## Known limits and next work

- The benchmark is synthetic, uses one repeated texture, and is tied to this Windows/D3D11 machine and toolchain.
- Draw-list composition is now linear in scene size but still the largest measured Release stage (4.241 ms at 10k Scene, 3.903 ms Game in the final run). Further work should use a sampling profiler and a more representative scene before adding complexity or caches across frames.
- GPU timing measures bgfx frame timing, not isolated framebuffer shader time.
- Next useful step: profile representative scenes in Release, optimize only the next demonstrated hot path, then evaluate complete Editor frame time before setting budgets.
