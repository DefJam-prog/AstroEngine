# 06.13 — Representative Release scene and full-frame profile

## Scope

Measure more representative 2D scenes in the complete Windows Release Editor and estimate end-to-end frame duration. The benchmark remains an opt-in `astro_editor --benchmark` path. It creates a unique temporary project and generated PNG fixtures, so user game assets are not modified. The repository has no tracked project scene or game image assets to use as a real-project benchmark.

## Build and run

```powershell
cmake --build build\06.4-editor-production --target astro_editor --parallel 4
build\06.4-editor-production\editor\astro_editor.exe --benchmark
```

The complete Release Editor build succeeded. The executable ran to completion with exit code 0. The benchmark keeps the normal Editor VSync setting, warms each full-editor scenario for 24 frames and records 48 measured frames.

## Scenarios and results

All views are 960×540. Each scenario uses 8 small textures, hierarchical chunk roots, tile sprites with varied rotations/scales, and transparent overlay sprites. Scene and Game views render simultaneously.

| Scenario | Visible sprites | Entities | Alpha overlays | Host frame p50 / p95 (ms) | Editor CPU before bgfx p50 (ms) | Scene + Game CPU p50 (ms) | `bgfx::frame()` call p50 (ms) |
|---|---:|---:|---:|---:|---:|---:|---:|
| chunked-tile-world | 337 | 340 | 48 | 16.672 / 17.518 | 1.972 | 0.261 | 14.757 |
| alpha-overdraw | 384 | 388 | 256 | 16.634 / 17.319 | 1.982 | 0.411 | 14.607 |
| mixed-world-effects | 329 | 332 | 128 | 16.652 / 17.551 | 1.885 | 0.397 | 14.625 |

For the 60 Hz display target, 16.667 ms is one frame budget. These measured p50 values are at that cadence; p95 exceeds it by about 0.65–0.88 ms. The Editor's CPU work before `bgfx::frame()` is about 1.9–2.0 ms p50. `bgfx::frame()` consumes about 14.6–14.8 ms due to pacing/VSync. Therefore, this measures observed interactive frame duration, not the uncapped CPU throughput of the renderer.

The instrumented BGFX CPU frame interval was about 16.6 ms and the reported GPU frame timer about 16.5 ms. BGFX `latencyTotal` and `latencyPresent` values were unavailable in this run. Given the present/pacing behavior and unavailable latency counters, these BGFX frame timer values are not treated as pure GPU execution time. They must not be compared as if they were GPU workload duration.

The direct offscreen-view profile for these same scenes reported the following additional CPU numbers:

| Scenario | Scene CPU p50 / p95 (ms) | Game CPU p50 / p95 (ms) | Paired BGFX frame timer p50 / p95 (ms) |
|---|---:|---:|---:|
| chunked-tile-world | 0.109 / 0.178 | 0.098 / 0.200 | 0.101 / 0.125 |
| alpha-overdraw | 0.126 / 0.191 | 0.107 / 0.180 | 0.159 / 0.284 |
| mixed-world-effects | 0.171 / 0.227 | 0.154 / 0.197 | 0.104 / 0.214 |

This confirms that, at these modest sprite counts, Scene/Game CPU preparation and submission are a small fraction of the complete Editor frame. The cost is dominated by the VSync-paced `bgfx::frame()` and other Editor work. The full-frame counter reports one extra visible sprite in the first and third scenarios versus the direct-render input count (336 and 328); entity totals match. This small reporting discrepancy does not affect timing, but should be resolved before using this counter for automated assertions.

## Validation

- Release Editor build: passed; `cmake --build build/06.4-editor-production --target astro_editor --parallel 4`.
- Release benchmark: passed; exit code 0, with all three full-frame scenarios reporting 48 measured frames.
- Debug Editor target: passed.
- Debug all-target build: failed linking `astro_2d_playground` with MSVC `LNK1104` for `astro_runtime_sdl_render2d.lib`. The archive exists at `build/stack-spike/engine/runtime/astro_runtime_sdl_render2d.lib`, while the generated playground link command references it as a build-root-relative path.
- Debug CTest after the failed all-target build: **35/37 passed**. The playground smoke could not start because that executable had not linked; project-preview smoke consequently also failed to launch it. The remaining 35, including `editor.smoke`, passed.

The Debug sample link-path issue is reported rather than masked by copying or relocating build outputs. It prevents claiming a clean full regression run for this profile.

## Limits and follow-up

- The data is one Windows x64, MSVC Release, D3D11 machine/build, with VSync enabled. It is not a platform-independent performance target.
- Scene content is deterministic synthetic 2D content. It covers hierarchical tiles, texture switches, transparent overlays and a mixed pattern, but not a production project, large textures, UI-heavy scenes or gameplay CPU workloads.
- The BGFX latency counters are unavailable, and the frame timer should not be interpreted as isolated GPU time.
- Resolve the generated Debug sample link path, rerun all-target build and all CTest tests, then measure a user-provided representative project or an approved checked-in benchmark scene. No separate frame-time budget has been approved.
