# 06.21 — Puzzle campaign format design

## Scope

Defined a proposed versioned file contract for Puzzle campaign order and transitions. This is a documentation/design slice only. It does not implement or claim a campaign parser, writer, editor, runtime resolver, or migration.

## Proposed contract

- UTF-8 text file: `<project>/Puzzle/Campaigns/<campaign-id>.astro-puzzle-campaign`, header `ASTRO_PUZZLE_CAMPAIGN 1`.
- Ordered, contiguous `LEVEL` records define presentation order; `START` separately selects the entry ID. Order does not implicitly create transitions.
- Each listed level has exactly one final `DEFAULT` transition to another campaign level or `END`. Optional `SCORE_AT_LEAST` rules appear before the default in strictly descending threshold order and use the completed Puzzle level's final score when the host requests one resolution.
- IDs refer to level files in the same project. All references must resolve in the campaign, all listed levels must be reachable from `START`, and missing/mismatched level assets reject campaign start.
- Bounds, UTF-8, unknown-version/condition behavior, example, cycles, path containment, and future tests are specified in [PUZZLE_CAMPAIGNS.md](../PUZZLE_CAMPAIGNS.md).
- Future catalog rename must not leave dangling campaign references. A later implementation must refuse referenced renames or update dependent files through an explicit validated operation.

## Risks and limits

The format is a design proposal that must be reviewed against the future campaign runtime before a parser is committed. v1 intentionally supports only score-threshold branches and fallback transitions. Campaign files, content migration, transition UI, runtime progression, and level-reference-aware rename remain unimplemented. No user level files or progress slots were changed.
