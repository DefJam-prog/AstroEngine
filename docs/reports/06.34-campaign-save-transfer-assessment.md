# Подэтап 06.34 — Оценка безопасного переноса сохранений Puzzle-кампании

**Результат: design-only.** Выполнена проверка существующих контрактов; код и данные сохранений не менялись.

## Что установлено

- Namespace Editor сохранений разрешается как SDL user-data root + `.astro/puzzle-save.settings` subdirectory + `PuzzleCampaigns/<campaign-id>`.
- Копия настроек проекта сохраняет namespace и может делить те же слоты с исходным проектом. Изменение subdirectory создаёт другой путь, но само по себе не переносит файлы.
- `PuzzleCampaignSaveAdapter` записывает ID кампании в custom state и при загрузке сравнивает его с ожидаемым ID. Несовпадение возвращает `VersionMismatch`. Поэтому копирование слотов после переименования кампании не является рабочей миграцией.
- Generic `SaveStore::inspect` не раскрывает campaign custom state наружу. Нынешний API не предоставляет достаточного read-only preview, чтобы до записи подтвердить identity и совместимость каждого слота.

## Безопасная граница и план будущей функции

1. Первую версию переноса ограничить одинаковым campaign ID. Перенос идентичности/содержимого между разными ID требует отдельной versioned migration спецификации и не входит в простое копирование.
2. Добавить read-only preview без создания каталогов и файлов: source/target, slots 0–9, размер, отсутствующий/валидный/повреждённый слот, восстановление из `.bak`, незавершённые временные файлы и конфликт каждого целевого имени.
3. Preview должен проверять containment и reparse/symlink-компоненты обоих путей. Неизвестные файлы не удалять и не включать в перенос молча.
4. Отдельная операция записи должна заново проверить план непосредственно перед копированием, отказаться от существующих целевых слотов по умолчанию, копировать (не перемещать), сохранять источник и публиковать каждый слот через временный файл с атомарной заменой только при отсутствии конфликта.
5. Перед запуском этой записи показать человеку точный список файлов и итог назначения и запросить отдельное подтверждение. В 06.34 оно не запрашивалось, поскольку никаких записей выполнять не планировалось.

Текущий SaveStore способен восстановить читаемый слот из backup при штатной загрузке, но не предоставляет простого экспорта выбранного восстановленного представления. Будущая реализация должна решить это на уровне SaveStore, а не копировать неподтверждённые байты повреждённого primary-файла как будто они валидны.
