# 06.37 — Campaign save transfer preflight

Date: 2026-11-15
Scope: define and test a no-write final revalidation contract for a future same-ID campaign save copy. No transfer, migration or UI write action.

## Result

Added `revalidatePuzzleCampaignSaveTransferPreview`. It re-runs the existing read-only preview against the preview's canonical source/target paths and returns one of:

- `Ready` — source state is unchanged, contains at least one valid or backup-recovered campaign slot, has no invalid/mismatched/oversized entries or unexpected artifacts, and target slot paths are clear.
- `StaleSource` — any captured source slot state, byte count, primary/backup presence or content fingerprint changed.
- `StaleDestination` — target directory existence or expected slot collision state changed since preview.
- `DestinationConflict` — the preview is current but any expected primary/backup target path is occupied.
- `SourceNotTransferable` — source contains no save slots, invalid/mismatched/oversized slots, or unexpected artifacts.

Source primary and backup fingerprints use bounded FNV-1a over the exact bytes. The save format already limits accepted saves to 4 MiB; larger files remain visible to preview but cannot produce a complete fingerprint and therefore cannot return `Ready`. FNV-1a here only detects ordinary content changes; it is not cryptographic integrity or a security mechanism. Collision detection checks path existence, so zero-byte files and directories at expected destination slot names also block preflight.

The function only reads and returns diagnostics. It never creates a directory, copies/replaces files, repairs a save or mutates the source. `Ready` is not approval or a lock: future code must revalidate immediately before its write, use exclusive target creation, preserve source bytes and request explicit confirmation for each transfer. Atomic behavior and partial-failure cleanup remain to be designed before a writer is implemented.

## Known limitations and next step

- Revalidation is point-in-time and FNV-1a is not collision-resistant. A future writer must create targets exclusively and verify the source through stable opened handles; a preflight result alone cannot prevent a later race.
- No snapshot compatibility against current authored campaign rules is performed.
- The existing Ninja/MSVC dependency database did not record Editor header dependencies for `main.cpp`; incremental builds after public header changes may use stale Editor objects unless dependency scanning is corrected or a clean build is used.
- No copy, overwrite, merge, repair, migration, settings persistence or UI confirmation button exists.

Next recommended substage: **06.38**, define and test the file-level copy transaction, exclusive-create policy and failure/rollback reporting in isolated fixtures. Only after that contract is accepted should a later separately confirmed substage add a user-facing operation that writes save data.
