# 06.40 — Recovery journal for interrupted campaign save transfers

## Implemented

Before creating any copied slot file, the runtime exclusively writes and flushes a bounded `.astro-campaign-transfer.pending` record in the target directory. Version 1 records the safe campaign ID and planned primary/backup artifact slot, byte count and FNV-1a fingerprint. The journal includes no arbitrary file paths or save payloads. On normal success or handled rollback, the runtime removes only the exact journal bytes it created.

On a later preview, the runtime parses the record with strict size, version, field, slot-count and duplicate checks. It compares each planned destination artifact and reports `Complete`, `Partial`, `Missing`, `Changed` or `Unsafe`. An invalid/torn record is shown as a diagnostic. Any pending record makes preflight return `RecoveryRequired` and blocks a new copy.

The Editor shows the journal path and every classified artifact path. A separate confirmation can acknowledge a valid unchanged journal; the API re-inspects the record and artifacts before deleting only the journal. No save file is removed, repaired or overwritten. The user manually inspects incomplete/changed files. After the journal is acknowledged, ordinary conflict checks continue to block overwriting any slot file still present.

## Tests and results

The integration test launches itself as a child on a Unicode temporary source and target. The child performs the real copy and calls `_Exit(77)` from the progress callback after the first artifact, bypassing rollback and process cleanup. The parent verifies that the recovery journal survived, the first artifact is complete, and the next artifact is missing. It confirms that preflight and retry are blocked, that acknowledgement without confirmation fails, and that confirmed acknowledgement removes only the journal while preserving the save file. The test also verifies handled cancellation removes its journal and that the surviving file remains a destination conflict. Editor smoke renders an isolated interrupted-copy record and verifies it is exposed in the UI. No real project or user AppData saves were used.

## Limitations

- The recovery API reports but does not resume a transfer or remove partial/changed slot files. Manual review is required; acknowledgement removes only the journal.
- A malformed/torn journal cannot be acknowledged through the API and requires manual inspection/removal.
- FNV-1a is a bounded diagnostic fingerprint, not a cryptographic integrity check or proof of file ownership.
- The test verifies abrupt process termination between artifacts. It does not simulate a mid-system-call power failure, and flushing the journal file does not guarantee its parent directory entry survives sudden power loss on every filesystem.
- The Git worktree was already dirty with 170 entries. No user changes were staged, committed, pushed, reset or deleted; real player-save folders were not used.
