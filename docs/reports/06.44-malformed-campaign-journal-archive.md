# 06.44 — Explicit archive of a malformed campaign transfer journal

Historical implementation report. Its retirement behavior was superseded by 06.45 after identifying the path-based deletion TOCTOU race. Current behavior preserves the original malformed journal; see [06.45 report](06.45-race-safe-malformed-journal-archive.md).

## Scope

Implemented only the recommended 06.44 operation: separately confirmed archival and retirement of a readable bounded malformed journal. No save-slot cleanup, journal repair or later substage was started.

## Behavior

- Added `archiveMalformedPuzzleCampaignSaveTransferJournal(recovery, explicitlyConfirmed)`.
- Only a displayed journal classified `Malformed` is eligible. It must be present, readable within the 4096-byte cap, and still byte-identical to the preview.
- Runtime re-inspects the target, rereads the raw journal and checks exact size/fingerprint. It derives an adjacent archive path from the journal fingerprint and creates it exclusively.
- If that archive path already exists, runtime accepts it only when it is a regular readable file with exact identical bytes. A different or unsafe occupant is never replaced.
- Runtime rereads the archive and the source, then re-inspects the source immediately before removing only the original journal. If checks fail, the original remains. If retirement fails after archive verification, both are preserved and the operation reports failure.
- No campaign slot artifact is parsed, read, changed or removed. Editor shows a separate confirmation with the journal path and target folder and reports the archive path on success. A successful action refreshes the preview; the invalid journal no longer blocks transfers.
- Tests cover no-confirmation refusal, success, archive collision, changed-after-review refusal and Editor smoke using only temporary fixtures.

## Limits and next step

This action retires only readable malformed journals. Unreadable, unsafe and oversized records still require manual handling. Fingerprints are non-cryptographic, and the implementation does not lock against another process changing the journal between the final recheck and removal. No real project/user save directories were opened. Next recommended work: 06.45, assess race-safe retirement/locking across Windows and future POSIX targets before broadening journal cleanup. Do not begin without confirmation.
