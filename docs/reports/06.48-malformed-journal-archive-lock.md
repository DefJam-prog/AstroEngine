# 06.48 — Lock malformed-journal archive

## Scope and behavior

The archive API now participates in the journal lifecycle lock introduced in 06.47. It first validates the displayed recovery preview and exact bounded malformed bytes by path, then acquires a lease for the source journal, rereads and compares exact bytes through that same handle, and holds the lease until the adjacent archive has been created or verified. It rereads the source through the held handle before returning success. If another cooperating copy, resume, acknowledgement or archive operation holds the lease, the request fails before creating an archive.

The malformed source journal remains in place and continues blocking copy/resume until manual review. The archive path is still exclusively created, existing identical archives are accepted, and different occupants are never replaced. Save slot files are not opened, modified, or removed. The file format and public API are unchanged.

On Windows, the source uses `LockFileEx`; a competing range lock causes a fail-closed result. Path-based classification happens before locking because Windows denies second-handle reads from a byte range protected by the exclusive lock. On POSIX, the source lease uses `openat`/`O_NOFOLLOW` and advisory `flock`; the test holds the lock in a separate process. POSIX locks coordinate only participants that honor the protocol and do not defend against arbitrary local writers.

## Limits

The implementation does not delete, repair, or migrate malformed journals. POSIX `flock` is advisory, and `fstatat` plus `unlinkat` is not an atomic protection against a hostile process that ignores the lock. Parent-directory durability after sudden power loss is not guaranteed. Tests use temporary fixtures only; no project or user save-data directories are accessed.
