# 06.50 — Staged atomic no-replace journal archive publication

## Scope

The confirmed operation for archiving a readable malformed campaign-transfer journal now writes to a unique temporary file beside the deterministic archive path. It flushes and rereads the staged bytes through the held handle, then publishes without replacing an existing destination. The original malformed journal remains in place under its lifecycle lease. Save slots and candidate files are not changed. No save format, public API, or dependency changed.

On Windows, publication uses `SetFileInformationByHandle(FileRenameInfo)` with `ReplaceIfExists=FALSE`. On POSIX, it verifies that the staging directory entry still names the held inode, uses same-directory `linkat` to publish the final name without replacement, verifies the final inode, then removes the staging link. POSIX attempts file and directory `fsync` around publication and cleanup. A staging file left by a terminated process is not trusted or removed automatically; a later attempt selects another unique name.

## Limits and risks

- Tests model stale staging files and final-path conflicts; they do not terminate the process mid-write or simulate kernel crash/power loss.
- A pre-existing partial/conflicting final archive still fails closed and needs manual review. This step does not automatically identify or repair old 06.49 residue.
- Staging residue from a real process interruption is preserved for inspection and does not block a retry. Failed publication cleanup is attempted only through the held staging lease and exact-byte/object checks.
- POSIX `flock` coordinates cooperating processes only. POSIX filesystem durability varies despite `fsync`; this prototype does not promise power-loss durability. Windows directory durability is filesystem-dependent.
- The Windows full CTest configuration ran the 40 registered tests for the selected modules; this configuration did not enable the optional SDL editor, Game UI demo, or C# host.
