# 06.53 — Read-only archive conflict diagnostics

## Scope and result

Implemented the 06.53 follow-up to the 06.52 archive-conflict assessment. The runtime now exposes `inspectMalformedPuzzleCampaignSaveArchive` for the deterministic archive path associated with a currently displayed, revalidated malformed journal. Editor reports the exact path, object kind, observed size when applicable, bounded byte comparison and a platform diagnostic. No new dependency or save-format change was introduced.

The check is read-only. Windows opens the final object with `FILE_FLAG_OPEN_REPARSE_POINT`; POSIX uses `fstatat` with `AT_SYMLINK_NOFOLLOW` and `openat` with `O_NOFOLLOW`. The source journal is revalidated and held under its existing lease while inspection runs. Regular archive content is read only when at most 4096 bytes, then the held object's identity/size/time metadata is checked again. Results distinguish missing, regular file, directory, link/reparse point, other, unavailable, and content states exact, different, prefix, oversized or unavailable. A prefix match describes bytes only; it does not establish authorship or prove a prior AstroEngine write.

Editor invokes the inspector after archive creation is refused and displays it in the recovery panel. Inspection does not create or modify files. Archive code still refuses to replace any differing occupant; slot files and the malformed source remain untouched.

## Tests

The campaign-save integration fixture covers missing, exact, different, prefix, oversized (4097-byte), directory, and symbolic-link final occupants. Link checks use a no-follow classification and preserve the referent; Windows skips link assertions if the test process lacks the required link privilege. The tests compare the malformed journal, candidate slot and owner sentinel before/after inspection. Editor smoke verifies a successful exact archive first, then converts only its isolated temporary archive fixture into an unrelated sentinel and checks the UI inspection result and source/slot preservation.

## Limits and next recommendation

The FNV-derived name and byte comparison are not cryptographic ownership checks. Filesystems and permissions can prevent reading or link test setup; those cases fail closed or skip only the platform-dependent link assertion. Tests cover cooperative locks and controlled fixtures, not arbitrary hostile concurrent path replacement, kernel crashes or power-loss durability. The UI offers no operation to remove, move, overwrite or repair an unknown occupant.

Recommended next substage: **06.54 assessment of an explicit user-directed “preserve as a new copy” workflow** for unknown occupants, including no-overwrite naming, confirmation wording and recovery behavior. Do not implement deletion or replacement as part of that assessment.
