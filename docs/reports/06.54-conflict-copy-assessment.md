# 06.54 — Assessment of copy-aside for archive conflicts

## Scope

This is a policy and test-design assessment only. No runtime code, Editor UI, save format, test source, build configuration or user data was changed. It follows 06.53 read-only archive conflict diagnostics and the staged no-replace publication model from 06.50.

## Finding and candidate policy

An explicit copy-aside can preserve an unknown occupant before an operator inspects or resolves the conflict manually. A copied file is still untrusted: its bytes, prefix, deterministic source name and successful copy do not show who created it or whether it is a valid campaign journal. Copy-aside must not make the ordinary archive operation retry automatically or clear the original conflict.

If a later implementation is approved, limit eligibility to the exact deterministic path associated with the displayed/revalidated malformed journal, and only when the occupant is a readable regular file no larger than 4096 bytes. Do not follow a Windows reparse point or POSIX symlink. Directories, links, special files, unreadable files and oversized files remain ineligible.

Require a separate confirmation that displays the canonical source path, generated adjacent destination path, exact byte count and a clear statement that the source is unknown/unverified. Do not display file contents. Generate a name distinct from the deterministic archive path, stage in the same directory, publish atomically without replacement, and retry with another generated name on collision. Hold/revalidate the same no-follow source object through reading and verification; if identity, size or content changes, abort. Preserve the source occupant, malformed journal and every save slot. The generated copy is evidence for manual review only and is not parsed, trusted or registered as an archive.

This action writes an additional file in the user's campaign-save directory, so confirmation must occur after the user has reviewed the exact destination. A successful copy does not resolve the original deterministic-path conflict. The operator still decides how to inspect and handle it. Any later move or removal would be a separate destructive action with separate confirmation and tests.

## Dependencies and risks

- Reuses the 06.53 no-follow classification/revalidation and 06.50 same-directory staged no-replace publication patterns; no new library is needed.
- The hard part is maintaining source identity across review, confirmation and copy while preventing path replacement. Tests must exercise source replacement and destination races on each platform.
- A second copy may duplicate sensitive or malformed data. Confirmation should disclose the exact destination and the fact that authorship is unknown; avoid content previews.
- Staging files can remain after process interruption. The future UX must report that state and must not delete unrecognized staging or final occupants.
- Filesystems may differ in atomic rename/link and durability guarantees. Process-kill tests are not proof against power loss or hostile local writers.

## Acceptance criteria for a future implementation

1. Cancel or stale preview writes nothing.
2. Only bounded regular files are eligible; reparse points, symlinks and special objects are never followed.
3. The published copy is byte-for-byte identical, uniquely named adjacent to the original, and never replaces an existing destination.
4. Source identity/content is rechecked while held; a changed or replaced source blocks publication.
5. The original conflict, malformed journal, candidate save and all slot files remain unchanged.
6. Copy success is labeled unverified and leaves the deterministic conflict unresolved.
7. Tests cover exact/different/prefix/empty/size boundary/oversized data, permissions, link refusal, destination collision, Unicode paths, confirmation cancellation, source races and process interruption before and after publication on Windows and POSIX.

It emitted existing C4189 unused-local warnings in `editor/main.cpp`, but no build errors. WSL Ubuntu Release build reported `ninja: no work to do`. ## Decision and next step

Adopt the above as a candidate policy, not as a promise that copy-aside exists. Keep all conflict handling read-only until a separately approved implementation stage.
