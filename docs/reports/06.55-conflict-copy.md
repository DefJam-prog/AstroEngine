# 06.55 — Explicit copy-aside for archive conflicts

## Scope

Implemented only the user-confirmed 06.55 substage following the 06.54 assessment. The action preserves a bounded, unknown file occupying the deterministic malformed campaign-journal archive path as a separate adjacent copy. It does not resolve or retry the conflict.

## Behavior

- Runtime preview accepts only a differing readable regular file, no larger than 4096 bytes. Exact journal matches are already reusable and are not offered for copy. Links/reparse points, directories, other object types, unavailable files and oversized files are rejected.
- Preview captures bytes and source identity and chooses an unused adjacent destination without writing. The Editor shows source and destination paths, byte count and an explicit statement that the author's identity is unknown and the copy is unverified. Cancel creates no output.
- Confirmation reacquires and retains a no-follow source lease, rechecks the same source identity and exact bytes and revalidates the malformed transfer journal. It writes a unique same-directory staging file and publishes to the generated destination atomically without replacement.
- Source archive occupant, malformed journal and candidate slot are preserved. The copied bytes are not interpreted as a campaign archive; successful copy does not clear the conflict or start another archive attempt.
- If the process stops before publish, staging may remain. If it stops after publish, the final copy exists and platform-specific staging residue may remain. These artifacts are intentionally not auto-cleaned.
- The Editor smoke runs the same confirmation handler with an isolated temporary fixture and compares the resulting bytes and preserved inputs. It is not a manual visual click-through of the dialog.

## Limitations and risks

The copy is unverified raw evidence and does not establish who created the occupant or whether it is a usable AstroEngine archive. The workflow does not clear the original conflict. POSIX advisory locking only coordinates cooperating processes. Tests demonstrate process termination at selected operation boundaries on the current Windows and WSL filesystems; they do not demonstrate kernel crash, power-loss durability, arbitrary hostile local path replacement or every filesystem's semantics. There is no dedicated Unicode-path assertion for this new copy operation. The UI confirmation logic is smoke-tested through an isolated fixture, not manually clicked or visually inspected.
