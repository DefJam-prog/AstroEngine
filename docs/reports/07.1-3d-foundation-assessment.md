## Candidate evaluation

### Rendering

The already prepared bgfx dependency is a sensible first renderer adapter candidate. Upstream currently lists Direct3D 11/12, Metal, OpenGL, OpenGL ES, Vulkan and additional backends, and its repository uses BSD-2-Clause. AstroEngine has actually compiled and smoke-tested only its existing Windows x64/MSVC/D3D11 setup. The upstream platform list is not proof that this project's adapter, shaders, packaging or GPU tests work on macOS/mobile. Reuse it only behind a distinct optional renderer target; keep core and headless builds independent.

### glTF parsing

The Khronos glTF specification describes an API-neutral asset delivery format; it is not a guarantee of a complete importer. The reviewed `cgltf` header is a C99 single-file parser, upstream version 1.15, with MIT notice. Its own API documentation states that external buffer contents are not automatically loaded; caller-supplied URI resolution is required. This aligns with AstroEngine's asset boundary only if the importer validates canonical project containment, limits file sizes/counts, rejects unsupported required extensions, and writes only derived cache data. Do not alter source glTF/GLB or images. cgltf is a candidate, not vendored, pinned or tested here.

### 3D physics

Jolt's upstream README currently documents C++17, MSVC 2022+/Clang 16+/GCC 12+, an STL-only dependency, a CMake FetchContent example, Windows/Linux/macOS/Android/iOS platform support, and its repository carries an MIT license. These declarations make it a strong candidate for the future optional 3D physics adapter, but are not an AstroEngine build, ABI, CI, size or performance result. Do not add it to core or default runtime now. Box2D is a 2D library and does not satisfy the 3D physics item.

## Recommended staged implementation

1. Define backend-neutral mesh buffers and camera pose/projection with explicit coordinate, handedness, clip-depth and near/far conventions. Add unit tests for finite values, invalid dimensions, projection, transform and index bounds. Avoid changing existing Scene serialization during this first contract step.
2. Build a procedural triangle/cube rendering sample through an optional bgfx adapter, with Editor/runtime smoke checks for visible output, resize/depth behavior, plus frame-time and build-size measurements. Keep these metrics as observations until the user approves budgets.
3. Add a limited glTF 2.0/GLB importer behind an optional asset-import target, beginning with static triangle primitives and explicit supported-feature diagnostics; test malformed/oversized buffers, missing resources, traversal, Unicode paths, unsupported required extensions and immutable source files.
4. Evaluate and prototype Jolt as a separate optional physics adapter with fixed-step determinism and collision integration tests. Check actual Windows and POSIX builds before enabling any configuration by default.

No rendering library version, glTF parser or physics dependency was pinned or downloaded in this assessment. Stage 07.1 is **in progress, not complete**. Recommended next substage: **07.1a — backend-neutral 3D camera/mesh contract and procedural bgfx triangle/cube visual smoke**. glTF and 3D physics remain later slices.
