## PBR data and source conventions

Use a metallic-roughness baseline for the first PBR implementation. The glTF 2.0 specification defines base-color, metallic and roughness factors, a metallic-roughness texture, emissive factor, normal/occlusion/emissive textures, alpha mode/cutoff and double-sided state. It defines base-color RGB and emissive RGB as sRGB inputs, while metallic-roughness data uses the B channel for metalness and G for roughness in linear space; alpha is governed by the material alpha mode. AstroEngine's schema should spell these rules out so imported values, GUI values and renderer sampling agree. See the [Khronos glTF 2.0 material and metallic-roughness specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#material) and its [PBR metallic-roughness section](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#material-pbrMetallicRoughness).

The editor color picker may present display-space color, but data crossing into the renderer needs one defined conversion convention. Scalar factors should be finite and range-checked; emission may need a later HDR intensity contract instead of silently overloading an LDR color. glTF alpha is not simply “opacity”: `OPAQUE`, `MASK` and `BLEND` affect render ordering and depth behavior. Those policies need visual and integration tests before exposing the settings as done.

Lighting, environment/ambient contribution, and shadow settings belong to Scene or renderer configuration, not to a reusable material asset. A shadow feature additionally needs light camera/projection, caster/receiver policy, bias and resolution controls; it should not be promised by a material editor screen alone.

## Renderer/dependency implications

The existing BGFX target is a useful backend adapter, but its current D3D11 cube binaries are not a PBR pipeline. Upstream BGFX documents that shaders are compiled offline with `shaderc` and provides separate examples for bump mapping, HDR, and shadow techniques. Therefore a future slice must own or deterministically generate shader sources/binaries, declare supported backend profiles, preserve shader source licensing/provenance, and report unsupported material features. A working example or backend list does not prove AstroEngine support on another platform. See the [BGFX shader resource documentation](https://github.com/bkaradzic/bgfx/blob/master/docs/bgfx.rst#resources) and [upstream examples list](https://github.com/bkaradzic/bgfx/blob/master/docs/examples.rst).

No third-party dependency is selected or installed in 07.2a. Keep current importer limits and source immutability. A later material/texture importer must extend project-root confinement, byte/dimension limits, cache digest/invalidation, cancellation and hostile-file tests; it must not fall back to arbitrary image decode or silently replace an unknown material with a reported success.

## Recommended implementation order

1. **07.2b — material asset model and serialization decision:** decide a versioned project asset envelope, stable material AssetId registration, defaults/ranges, unknown-field diagnostics, and texture-role references. Add unit and integration tests for validation, round-trip, migration, stale/missing IDs and command Undo/Redo.
2. **07.2c — bounded glTF material metadata:** preserve per-primitive source material assignment and supported core material factors. Keep unsupported required extensions and external texture dependencies explicit and test path limits/source immutability.
3. **07.2d — Editor authoring:** material workspace/Inspector with color, metallic, roughness, alpha, emission and texture replacement through the common typed command path; add a smoke test and example material.
4. **07.2e — lit preview slice:** extend mesh import/layout with normals and UVs, build a small offline shader pipeline, and demonstrate one directional light plus a deterministic test scene with visual tolerance checks. Choose a shader feature budget and performance budget separately.
5. **Later 07.2 work — broader light types, environment, shadow maps, and Game View/runtime parity:** each requires its own capability contract, visual tests, benchmark scenes and backend validation.

This sequence is a recommendation, not approval to start 07.2b. No shadow or PBR performance budget is currently approved.
