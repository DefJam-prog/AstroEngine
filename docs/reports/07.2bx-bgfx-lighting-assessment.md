# 07.2bx — BGFX DirectionalLight3D visual slice assessment

## Scope

Assess how the existing backend-neutral light packet can become visible in the current Windows Editor Scene/Game View renderer. This is an assessment only: no shaders, C++ behavior, assets, or dependencies were changed.

## Current boundary

- `SceneRenderPacket` already carries enabled `DirectionalLight3D` entries with stable IDs, linear RGB, bounded intensity, and normalized world direction.
- `BgfxSceneRenderer::render` currently submits each geometry item and material; it never reads `packet.directionalLights`.
- The runtime BGFX vertex layout is position/color/UV. `MeshVertex::normal` is not uploaded. Both project fragment shaders output flat base color and implement existing OPAQUE/MASK behavior only.
- The Editor currently pairs project fragment shaders with cached BGFX example vertex binaries (`vs_cubes.bin`, `vs_stencil_texture.bin`). They do not expose a normal varying.
- Built-in 3D primitives author normals. glTF imports may omit the optional normal channel. No renderer normal matrix, shader gamma policy, or light limit exists.

## Recommended next implementation slice

1. Add project-owned BGFX vertex shader source(s) and compile both color and textured lit programs through the existing local `shaderc` build step. The same program contract should be usable by Scene View and Runtime Game View; BGFX handles remain host-owned.
2. Upload normals when geometry supplies them. Compute the 3×3 inverse-transpose of each render item's world transform and apply it in the vertex shader; interpolate the transformed normal and evaluate Lambert response per pixel. Add CPU unit cases for rotation, non-uniform scale, hierarchy composition, and degenerate matrices. Do not use the world matrix directly for normals.
3. Implement direct Lambert diffuse in linear space: `baseColor * Σ(lightColor * intensity * max(dot(normal, -direction), 0))`. Keep existing unlit base-color output when there is no enabled light. Preserve alpha/cutoff behavior for the OPAQUE/MASK subsets already accepted by the adapter; leave BLEND and unsupported PBR inputs on the existing fallback.
4. Set a fixed shader capacity of **4** directional lights. Packet construction is already sorted by EntityId; consume the first four and add a diagnostic for overflow instead of silently implying all lights were rendered. The number is a prototype limit, not a performance budget.
5. Define linear-to-display output conversion for the BGRA8 offscreen Scene/Game targets and sRGB swapchain. The color pipeline already decodes source images into linear values; applying lighting in gamma space would be incorrect. Validate the chosen output transform with a rendered screenshot rather than inferring correctness from shader compilation.
6. Preserve an unlit path for geometry that lacks normals and surface a diagnostic. Do not invent a normal or silently mark missing normals as correctly lit. Do not mutate imported source assets to generate normals in this slice.

## Visual acceptance proposal

Add an Editor Game View smoke in a disposable project with a known active camera, a cube and two oppositely oriented normal-bearing surfaces, controlled base colors, one authored directional light, and an otherwise identical no-light run. Capture both BGRA8 targets. Assert:

- the no-light capture retains the prior unlit color/pixel coverage within a broad driver-tolerant range;
- the light-facing surface is brighter than the reverse-facing surface by a minimum luminance separation;
- both meshes submit through the BGFX adapter with no fallback/diagnostic;
- the no-normal mesh remains visible through the unlit fallback and reports that it did not receive directional lighting;
- existing OPAQUE, MASK cutoff/mipmap, textured submission, and unsupported-material fallback tests continue to pass.

This is a bounded visual detector, not a cross-driver pixel golden. Exact lighting intensity/color budgets remain product decisions.

## Dependencies and risks

- No new library is needed; this host already has BGFX, the local `shaderc`, and the optional Runtime BGFX adapter.
- The present shader build is Windows/D3D11 (`shaderc --platform windows -p s_5_0`). This does not establish compatibility with Metal, Vulkan, OpenGL, Android, or iOS; additional platform shader builds and smoke runs are future work.
- Normal math must match the engine's existing matrix composition conventions. Non-uniform parent scale and rotations make a direct world-matrix multiply incorrect.
- Light count is a fixed GPU uniform constraint for this prototype; overflow diagnostics and deterministic order are needed for predictable output.
- Scene/Game BGRA8 offscreen targets are later composited by an sRGB swapchain. A mistaken gamma transform can produce plausible but numerically incorrect images.
- Existing BGFX adapter and Scene View have distinct renderer fallback behavior; the acceptance run must prove which route drew each item.
- This first slice remains direct diffuse only. No specular response, PBR metallic/roughness, emissive combination, ambient probe, point/spot light, shadows, or mobile backend is implied.
