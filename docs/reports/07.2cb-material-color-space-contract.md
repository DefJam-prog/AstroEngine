# 07.2cb — Material color-space contract assessment

## Result

The material semantics should be explicit, but the color-space tag should not be duplicated in `.astro-material` for roles whose meaning is already defined by the material/texture role. The renderer adapter still needs an explicit conversion contract. The current BGFX implementation does not consistently execute that contract end to end; the textured lit path appears to decode base-color RGB twice.

This was an assessment-only substage. No runtime code, API, schema, assets, or dependencies were changed.

## Semantic contract

The existing `MaterialAssetData` comment and `docs/FILE_FORMATS.md` already describe numeric color factors as linear-light values and texture interpretation by semantic role. The Khronos glTF 2.0 material specification states that `baseColorFactor` is a linear multiplier; baseColorTexture RGB uses the sRGB transfer function and alpha is linear. `COLOR_0` is an additional linear multiplier. Emissive texture RGB is sRGB encoded; data textures such as normal and metallic/roughness use linear data. See the [Khronos glTF 2.0 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html), sections 3.9 and 5.22.

Recommended boundary: preserve these semantic role rules at import/material boundaries, and specify how each renderer backend decodes, filters and combines values in linear space and encodes final output. A general serialized `ColorSpace` field in `.astro-material` would duplicate role semantics and permit contradictory states; no evidence supports adding that field now.

## Current BGFX code path

| Path | Observed behavior | Assessment |
|---|---|---|
| Image input | WIC/runtime decoder returns BGRA8 identified as sRGB source data. | Suitable source representation for base-color role. |
| CPU preparation | `prepareLinearBaseColorMipChainBgra8` decodes RGB from sRGB, multiplies the linear factor, keeps alpha linear, and builds mip levels from these prepared values. | Output bytes are linear UNORM8, with 8-bit precision. |
| GPU base-color texture | Editor Scene View and Runtime BGFX create `TextureFormat::BGRA8` textures with `BGFX_TEXTURE_NONE`. | The API path does not request an sRGB texture view; shaders receive normalized stored values. |
| Lit texture shader | `scene_lit_textured.fs.sc` calls `srgbToLinear(color.rgb)` before applying the light. | Since CPU input has already been linearized, this appears to be a second sRGB decode. |
| Unlit texture shader | `scene_textured.sc` writes the sampled value directly. | CPU-linear bytes are not encoded back to sRGB in this branch. Existing no-light equivalence only preserves prior behavior; it does not validate displayed color semantics. |
| Render target/composition | Scene/Game offscreen attachments use ordinary `BGRA8`; BGFX host reset uses VSYNC without `BGFX_RESET_SRGB_BACKBUFFER`. | Output transfer and ImGui composition are not pinned by an end-to-end mid-tone test. This assessment does not prove a specific final display error on every D3D11 configuration. |
| Vertex color | Imported glTF `COLOR_0` is linear; the lit color shader multiplies it by diffuse and applies `linearToSrgb`. | The isolated vertex-color red-light smoke proves orientation/color presence, not its numeric transfer behavior. |

The same CPU base-color preparation and ordinary BGRA8 upload appear in both Scene View and the optional Runtime BGFX adapter. The color shader and textured shader have different input paths; the 07.2ca no-light comparison checks old-versus-new shader equivalence, not correctness against a reference color value.

## Existing tests and gaps

`runtime.base_color_texture.unit` covers CPU sRGB decode, linear factor multiplication, alpha and linear-space mip generation. BGFX texture/factor smoke tests cover sampling and coarse visible color families. `editor.runtime_bgfx_directional_light.smoke` covers face orientation and no-light image equivalence. These tests do not pass an sRGB mid-gray image and non-white linear factor through the complete lit and unlit BGFX sampling, shading, render-target, ImGui composition and screenshot path. Primary colors can miss a double-decode because their RGB channels are near 0 or 1.

## Recommended implementation acceptance for 07.2cc

1. Choose one ownership point for sRGB decode. Either keep encoded source bytes and request/verify an sRGB sampling view, or upload linear bytes and remove the shader decode. Never apply both conversions.
2. Apply `baseColorFactor` once in linear space and preserve alpha as linear coverage. Keep mip filtering in linear color space, with the existing alpha-mask coverage policy.
3. Define output encoding for Scene View/Game View offscreen targets, Runtime output, and final ImGui composition; encode exactly once for the chosen attachment/presentation configuration.
4. Add a BGFX pixel test with a non-primary sRGB mid-gray (e.g. channel 128), a non-white factor (e.g. 0.5), and tolerant expected display bytes. Check no-light, lit, and vertex-color cases separately; use an oriented light result whose expected linear multiplication is known.
5. Retain existing primary-color, source-texture, mask/mipmap, no-light equality and fallback regressions. Report the actual backend and target format; do not treat a D3D11 screenshot as a cross-platform golden.

For one full-diffuse reference pixel, sRGB `128/255` decodes to about `0.216` linear; multiplying by factor `0.5` gives about `0.108` linear and re-encoding gives an expected output near byte **93** (subject to sample/filter and target quantization). A test should compare the actual BGFX render/composition path against a tolerance, rather than treating the CPU helper's output bytes as display bytes.

No external dependency is indicated. No serialized schema change is recommended unless a future custom texture role cannot determine its interpretation from the role itself.
