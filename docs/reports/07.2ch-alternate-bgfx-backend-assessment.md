# 07.2ch — оценка доступности альтернативного BGFX backend

## Цель и границы

Проверить, можно ли на текущей Windows-сборке AstroEngine запустить Editor на альтернативном графическом backend BGFX. Это assessment-only подэтап: исходный код, renderer selection, shader pipeline, зависимости и настройки Windows не изменялись. Установка SDK, переключение renderer и запуск нового backend в этот подэтап не входят.

## Проверенные факты

- `vulkaninfo --summary` обнаруживает Vulkan loader **1.4.357** и устройство **AMD Radeon Graphics** с API **1.4.359**. Инструмент сообщает о нефатальном предупреждении при чтении registry для layer manifests, но перечисляет устройство.
- В локальном `build/spike-deps/bgfx/src/config.h` Vulkan включён как конфигурация BGFX по умолчанию для Windows, если сборка явно не переопределяет эту настройку. Наличие такого макроса не доказывает, что собранная библиотека AstroEngine содержит или активирует нужный renderer.
- Инициализация BGFX в Editor явно устанавливает `bgfx::RendererType::Direct3D11` и `fallback = false`. Следовательно, существующий запуск Editor не запрашивает Vulkan.
- Правила shader build в `editor/CMakeLists.txt` компилируют Scene View shaders только для `--platform windows -p s_5_0`. В `build/07.2d-release-clean/editor/shaders` отсутствуют SPIR-V/Vulkan-варианты.
- Переменные `VULKAN_SDK` и `VK_SDK_PATH` в окружении не обнаружены. Наличие системного Vulkan loader/драйвера не означает наличие Vulkan SDK для разработки.

Таким образом, на этом ПК есть Vulkan runtime и GPU-драйвер, но текущая конфигурация AstroEngine не предоставляет проверенного пути запуска Editor через Vulkan. BGFX-флаг в исходной конфигурации и наличие драйвера недостаточны для заявления о поддержке. Vulkan и другие альтернативные backends фактически не запускались.

## Команды и результаты

Проверка выполнялась в Windows x64 Release-конфигурации с уже имеющимися локальными зависимостями. Установка пакетов и сетевые загрузки не выполнялись.

```powershell
vulkaninfo --summary
cmake --build build/07.2d-release-clean --config Release --target astro_editor --parallel 8
ctest --test-dir build/07.2d-release-clean -C Release --parallel 1 --output-on-failure -R "^(runtime\.render3d\.color_contract\.bgfx\.smoke|editor\.runtime_bgfx_directional_light\.smoke|editor\.runtime_bgfx_game_view_texture\.smoke)$"
git diff --check
```

Фактические результаты:

- `vulkaninfo --summary`: Vulkan loader и AMD устройство перечислены; присутствует указанное выше нефатальное предупреждение о layer registry.
- Release build `astro_editor`: **успешно**, Ninja сообщил `no work to do`.
- Три сфокусированных smoke на существующем D3D11-пути: **3/3 прошли**. Они проверяют только текущую конфигурацию D3D11 и ничего не говорят о Vulkan.
- `git diff --check`: проходит после добавления отчёта.
- Полный CTest не повторялся: исполняемое поведение и исходный код не менялись.

## Ограничения и риск

Это проверка локальной доступности runtime и конфигурации проекта, а не GPU capability benchmark и не тест инициализации Vulkan в BGFX. Фактические compile definitions статической библиотеки BGFX здесь не подтверждены. Не проверялись Vulkan shader compilation, Editor initialization, представление Scene/Game View, точность кадра, производительность, другие драйверы или платформы. Предупреждение `vulkaninfo` также не было отдельно диагностировано, поскольку устройство успешно перечислено и проектный Vulkan smoke пока невозможен.

## Рекомендация

Следующий отдельный подэтап — спроектировать ограниченный test-only выбор renderer и сборку соответствующих SPIR-V shader variants, оставив D3D11 значением по умолчанию. Только после этого следует запускать отдельный Vulkan initialization/smoke на этой машине и сравнивать кадр с D3D11 baseline. Этот подэтап не начат.
