# 07.2cp — Vulkan extent after window resize

## Scope

Read-only diagnostics compare SDL drawable dimensions, the dimensions passed to `bgfx::reset`, BGFX statistics, Vulkan surface capabilities queried for the same Win32 HWND and BGFX screenshot TGA dimensions after resizing. No production rendering behavior or public API changed.

## Results on this Windows x64 AMD/Vulkan host

| Requested client size | SDL drawable at capture | `bgfx::reset` / stats | Vulkan `currentExtent` (min=max) | BGFX screenshot TGA | Game View target | readback |
|---|---:|---:|---:|---:|---:|---:|
| 1100×720 | 1100×720 | 1100×720 | 1100×720 | 1280×800 | 624×416 | 563/768 |
| 1280×800 | 1280×800 | 1280×800 | 1280×800 | 1280×800 | 624×416 | 768/768, maxDelta 0 |

At 1100×720, SDL, the BGFX reset dimensions/statistics, and a separately created Vulkan surface on the same HWND all agree on 1100×720. The Vulkan surface reports a defined `currentExtent` with min/max also 1100×720. The TGA written by `bgfx::requestScreenShot(BGFX_INVALID_HANDLE)` still measures 1280×800. BGFX's local Vulkan backend implementation sizes its screenshot readback from the selected `SwapChainVK::m_sci.imageExtent`, so this capture dimensions discrepancy is inside or downstream of BGFX's screenshot target selection, not an SDL drawable/current-surface mismatch. This does not yet prove which BGFX framebuffer is being captured or why it retains that size.

At 1280×800, all independent dimensions and the TGA agree. The screenshot viewport rectangle equals the 624×416 Game View target, all 768 comparison samples match with maxDelta 0, and five fixed pixel probes match.
