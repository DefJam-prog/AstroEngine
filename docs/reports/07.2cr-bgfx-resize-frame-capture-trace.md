# 07.2cr — BGFX Vulkan resize frame capture trace

## Scope

Reproduce the BGFX Vulkan screenshot extent discrepancy across a deterministic main-window resize sequence. No production resize behavior or vendor BGFX files were changed.

## Baseline and plan

Before edits, `astro_editor` Release was up to date. Focused tests produced 2 passes and 1 recognized Vulkan parity skip. The worktree had extensive preexisting modified and untracked project files; none were reset or cleaned. Recovery reference before edits: `refs/codex-recovery/07.2cr` → `5d6d0380038ef13d18f313f2b1c51277d317154d` (tracked worktree snapshot; untracked files remain in place).

The trace is enabled only in the fixed 1100×720 Vulkan tap CTest. It samples BGFX stats at reset and following frames, requests distinct screenshots, and reads each TGA header from a unique directory inside the build tree.

## Results

On this Windows x64 AMD Vulkan host:

- Baseline screenshot request at application frame 19: **1100×720**.
- Window growth 1100×720 → 1280×800: reset observed at frame 21; captures at frames 21–24: **1280×800** each.
- Window shrink 1280×800 → 1100×720: reset observed at frame 46. Stats still said 1280×800 at frame 46 and changed to 1100×720 at frame 47. Captures at frames 46–49 remained **1280×800** each.
- End-of-run tap screenshot: screen 1280×800, requested window/reset/backbuffer stats 1100×720, Game View target 624×416, measured rectangle `(288,217)+726×462`.
- Game View comparison: **563/768**, maxDelta **145**; alternate vertical orientation **564/768**. Existing 99.5% acceptance still fails, so the established parity test remains skipped.

One interim run between instrumentation iterations reported 768/768 and passed the parity comparison. The next repeated instrumented run and the final full Release CTest reproduced 563/768, so the one-off result is recorded as variable behavior, not accepted parity. The diagnostics reproduce that the mismatch follows the shrink transition; they do not establish why the backend screenshot extent remains large or provide a production fix.

## Next step

Trace the Vulkan backend's `SwapChainVK::update` and swapchain recreation state at the shrink boundary. The present evidence shows that public BGFX stats and screenshot `m_sci.imageExtent` diverge after shrinking; it does not yet show which backend branch retains the 1280×800 image extent. Preserve D3D11 default and the 99.5% acceptance requirement until the backend state transition is understood.
