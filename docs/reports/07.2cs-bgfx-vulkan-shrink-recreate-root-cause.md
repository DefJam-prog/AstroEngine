# 07.2cs — BGFX Vulkan shrink recreation root cause

## Scope

Trace the local BGFX Vulkan swapchain update/recreation state at the reproducible 1280×800 → 1100×720 shrink boundary. This stage diagnoses only; it does not retain a renderer or vendor patch.

## Backend trace and diagnosis

The backend log captured two swapchain creation states:

1. Initial: requested descriptor 1100×720; surface `currentExtent`, min/max and selected image extent all 1100×720.
2. Grow transition: surface `currentExtent`, min/max 1280×800; BGFX descriptor still 1100×720; `presentScaling=1`; selected image extent 1280×800.

After shrinking the surface to 1100×720, `RendererContextVK::updateResolution` received a request for 1100×720 while the backbuffer framebuffer/image remained 1280×800. `SwapChainVK::update` compared the requested descriptor to stored `m_desc`; both were already 1100×720, and `m_needToRecreateSwapchain` was false. Its recreation predicate therefore remained false. No `createSwapChain`/recreation log occurred after the shrink. This left `m_sci.imageExtent` at 1280×800 even after BGFX's public stats returned to 1100×720.

The per-frame TGA tap corroborated this state: baseline screenshot 1100×720; four captures after grow 1280×800; four after shrink still 1280×800. Final Game View readback was 563/768, maxDelta 145; the 99.5% parity contract remains unmet and skipped. The root condition is the mismatch between stored requested descriptor and actual image/current surface extent; a stable descriptor does not trigger recreation when surface extent has changed. This is confirmed only for the local BGFX revision and the current Windows x64 AMD Vulkan driver.
