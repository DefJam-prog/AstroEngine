# 07.2cw — Vulkan multi-cycle resize smoke

## Scope

Add a bounded, test-only Vulkan resize trace that performs two grow/shrink cycles in one Editor process. This increases local regression coverage where no second physical Vulkan host is available; it does not claim cross-driver validation.

## Baseline and recovery

- Required project docs were reviewed; no `AGENTS.md` exists.
- The worktree contained extensive earlier user/project changes; existing work was preserved.
- Windows has one physical Vulkan adapter (AMD Radeon Graphics). CMake/CTest 4.4.4 and MSVC 14.44/VS 2022 Build Tools are available.
- Existing Release target built with no actions before edits. Baseline resize tests passed **2/2**.
- Recovery ref: `refs/codex-recovery/07.2cw` → `95c8b14a188d55981696ee1b40010618dea9d53d` (tracked snapshot only).

## Implementation

`ASTRO_VULKAN_GAME_VIEW_RESIZE_CYCLES` is read only by the existing opt-in Vulkan resize-trace smoke. Its accepted range is 1–2; default is one cycle. Two cycles schedule window transitions at frames 20, 35, 50, and 65, finishing before the existing frame-89 final readback capture. The stress case takes two BGFX screenshots per transition (nine TGA files including baseline), keeping output bounded. CMake validates all four ordered transitions and the exact dimensions in every capture.

The first stress attempt intentionally exposed an interaction: the initial second-cycle schedule placed the final shrink after the existing frame-89 screenshot, so that test failed on a 1280×800 capture/readback. The schedule was moved earlier; the assertions stayed strict and the test then passed.

## Limitations and next step

The repeated transitions and readbacks ran on the same Windows x64 AMD Vulkan driver. They test resize state across consecutive transitions in one process, but do not validate another GPU, operating system, or BGFX revision. Keep Vulkan opt-in and D3D11 as the default. The next recommended step remains running this test on a second Vulkan host/driver; none was available here.
