# 07.2d — Scene material-slot bindings

## Scope

Add persistent project-material overrides to a Scene primitive selection, keep imported glTF source-material identity separate, expose changes as typed transactional commands, and retain old Scene compatibility. This substage does not add a Material Inspector, texture upload, PBR rendering, lighting, shadows, or normals/UV geometry data.

## Implementation

- `MeshRendererComponent` has an optional `materialOverride` AssetId. Zero means the glTF source material applies. The field is appended so existing aggregate initializers remain source-compatible.
- New components use MeshRenderer schema v2. The existing `set_mesh_renderer` API remains available; changing an existing component promotes it to v2.
- `entity.set_mesh_material_override` accepts `{entity, material}`. Validation requires an existing MeshRenderer and a well-formed AssetId; zero clears the override. Execution is transactional and supports Undo/Redo for both assignment and clearing.
- Scene output is now `ASTRO_SCENE 7`. Reader support remains v1–v7. Scene v6 MeshRenderer v1 loads with no override; saving that document writes a schema v2 v7 record. New v7 records require schema v2 and a material AssetId value, including zero for no override.
- `resolveMeshRenderer` keeps the imported source material index separate, returns the Scene override AssetId, and resolves nonzero overrides through AssetRegistry. Missing/stale references fail with diagnostics.

## Limitations and next slice

No editor GUI can choose the material yet; no render backend consumes this binding. Scene validation accepts stable nonzero IDs without project context, while the render3d resolver checks that the referenced material is registered and current. Windows x64 only was exercised. Next recommended substage: **07.2e — expose the Scene primitive material override in the Editor Inspector with registered-material choices and diagnostics**, keeping rendering out of scope until a separate implementation step.
