# 07.2d8 — Vulkan resize baseline capture timing

## Scope

Diagnose and fix the intermittent 1100×720 baseline screenshot mismatch in the Vulkan Game View resize stress smoke. The failure occurred before/around the first synthetic window resize; no production rendering behavior or resize algorithm is changed.

## Cause

The trace requested its baseline screenshot at frame 19. The first synthetic resize is scheduled at frame 20 and reaches the Editor's size-change handling in the following frame. BGFX transfers screenshot requests to its render thread and services them after rendering submitted work. The one-frame lead allowed the first resize and swapchain update to overtake the asynchronous baseline capture. Failed runs saved the supposed baseline at **1280×800**, while later trace entries showed the initial window at **1100×720** and then the scheduled grow/shrink transitions.

## Change

The trace now requests its baseline at frame 8, leaving multiple submitted frames before the first resize. The test still requires the same number of captures and validates each expected extent; no dimension or transition assertion was relaxed. Resize-trace capture remains opt-in and test-only.

Changed files:

- `editor/main.cpp` — moved the baseline trace capture from frame 19 to frame 8.
- `docs/DECISIONS.md` — D247 records the timing constraint and scope.
- `docs/STATUS.md` — records 07.2d8 outcome and platform limits.
- `docs/TESTING.md` — commands and results.
- This report.

## Limits

Repeated on one Windows x64 machine with an AMD Vulkan device. Other Vulkan drivers, BGFX revisions, operating systems, and a second display/host were not checked. The frame-8 lead is validated for the current smoke/host setup; screenshot capture still uses BGFX's asynchronous render-thread path.
