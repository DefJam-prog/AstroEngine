# 07.2m — glTF sampler and UV transform assessment

## Result

Completed an assessment only. No code, asset, source fixture, public API, serialized format, dependency, or runtime behavior changed.

## Current path

- `ImportedGltfTextureReference` retains an optional `samplerIndex`, but not sampler `wrapS`, `wrapT`, `minFilter`, or `magFilter` values.
- `GltfMaterialTextureBinding` retains `textureIndex` and `texCoord`; `KHR_texture_transform` values are not transferred into the binding. The importer emits an unsupported-feature diagnostic.
- Mesh import and `MeshData` provide UV0 only. The Editor Scene View diagnoses texture bindings that request a nonzero UV set and uses vertex-color fallback.
- The Scene View texture is created with one mip level. Each textured draw supplies fixed BGFX Clamp + Point flags.
- The importer currently rejects glTF files that declare any `extensionsRequired`; this blanket policy already prevents required-but-unsupported extensions from being accepted.
- Project `.astro-material` bindings have an image AssetId and `texCoord`, but do not carry sampler or transform data. This is a separate contract decision for any follow-up that aims to treat source materials and explicit project overrides consistently.

## Specification implications

The glTF 2.0 sampler defines independent S/U and T/V wrapping. Valid wrap modes are REPEAT (10497, default), CLAMP_TO_EDGE (33071), and MIRRORED_REPEAT (33648). `magFilter` can be NEAREST (9728) or LINEAR (9729); `minFilter` can additionally select four mipmap combinations (9984–9987). If no sampler is assigned, glTF requires repeat wrapping and an implementation-selected filtering policy. The current fixed Clamp + Point behavior therefore differs from core glTF's omitted-sampler wrapping and may differ from explicit samplers. [Khronos glTF 2.0 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

`KHR_texture_transform` is ratified and applies to each `textureInfo` binding, not to the image or sampler. It defines offset `[0,0]`, rotation `0` radians counter-clockwise, scale `[1,1]`, and an optional `texCoord` override. The affine transform can be applied to UVs in the shader and must not mutate the imported source/cached mesh. The override takes precedence over the base `texCoord` when supported. [Khronos KHR_texture_transform](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_texture_transform/README.md)

## Recommended implementation boundary

The next implementation should keep the established source/override/fallback selection rule and support only base-color in Editor Scene View, initially on UV0 and Windows D3D11. It should:

1. Preserve validated sampler settings and transform values in importer metadata. Apply glTF defaults deliberately; do not turn an omitted sampler into Clamp + Point.
2. Map all wrap modes and nearest/linear magnification and non-mip minification to BGFX per draw. The BGFX texture object can remain shared; sampler state is a submission property.
3. Define explicit behavior for mipmapped minification. Current uploads have one mip level. Either add a bounded mip-chain generator and create/upload all levels, or keep mip-dependent samplers on the existing diagnosed fallback until that work is complete. Never silently collapse mip modes to a non-mip filter.
4. Apply offset/rotation/scale to the selected UV in the textured shader (or another transient path) without editing mesh/source/cache bytes. A nonzero transform `texCoord` override remains a diagnosed fallback until corresponding vertex UV channels exist.
5. Decide whether project material overrides need per-binding sampler/transform fields and a versioned `.astro-material` migration. Until then, document their exact default sampling policy and avoid implying source-material parity.
6. Preserve and regression-test the importer's current fail-closed policy for `extensionsRequired`; if it is later narrowed to recognized extensions, a required `KHR_texture_transform` must remain a clear unsupported-feature error.

No new third-party dependency is indicated. Existing fastgltf and BGFX stages already provide metadata parsing and sampler flag mechanisms. Platform behavior beyond the existing Windows D3D11 prototype still needs separate validation.

## Proposed verification matrix for 07.2n

- Importer unit/integration: absent sampler, absent individual properties, every legal wrap/filter value, invalid/out-of-range indices and enum values, transform defaults, finite values, optional transform `texCoord` precedence, and regression coverage for the existing required-extension rejection.
- Transform unit test: identity, offset, nonuniform/negative scale, rotation, composition order, and invalid non-finite values against the Khronos affine formula.
- BGFX Editor smoke: a generated pattern with coordinates below 0 and above 1 distinguishes repeat, clamp and mirror; magnification/minification patterns distinguish nearest/linear; offset/scale/rotation produce expected coarse regions; unsupported UV and mip configurations retain the mesh with a visible diagnostic.
- Regression: existing source-vs-project material priority, UV fallback, missing-image fallback, source-byte immutability and full Release CTest.
- Keep visual checks coarse and fixture-owned; do not add or rewrite user assets. A cross-driver exact golden is not appropriate for this D3D11-only slice.
