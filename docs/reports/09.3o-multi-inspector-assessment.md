# 09.3o — оценка массового Inspector

## Цель и исходное состояние

Оценить безопасный первый шаг для Inspector после появления множественного выделения в 09.3n. Это подэтап оценки: код, публичное поведение, API и пользовательские сцены не менялись.

Перед оценкой:

- `git status` показал branch `main` на `origin/main` с большим числом уже изменённых и неотслеживаемых файлов. Базовый HEAD: `8d7ab7c`. Ничего не сбрасывалось и не очищалось.
- CMake/CTest 4.4.4 и Ninja доступны; MSVC доступен через VS 2022 `VsDevCmd.bat` (отдельный `cl.exe` в PATH не найден).
- `rg --files -g AGENTS.md` не нашёл дополнительных репозиторных инструкций.
- Release build был актуален: `ninja: no work to do`.
- Профильный регрессионный набор — **5/5 passed**.
- Последний полный CTest после 09.3n: **131 passed, 0 failed, 1 skipped из 132 за 144.73 s**. Пропускался только mixed-DPI smoke из-за отсутствия подходящей пары дисплеев.

## Наблюдения по текущим контрактам

- `drawInspector` получает только `selectedEntity`; в Hierarchy отдельно хранится `hierarchySelection`. Групповой Inspector пока отсутствует.
- `Scene::createEntity` создаёт каждому объекту Transform component. Значит, Transform — общий обязательный компонент без неоднозначности «у части объектов есть, у части нет».
- `entity.set_transform` v1 принимает весь local Transform одного EntityId и является транзакционным. Вызов команды циклом по группе создаст несколько записей Undo, поэтому не подходит для одного действия пользователя.
- `CommandTransaction` может собрать несколько шагов, а `TransactionHistory` применяет их одной записью и откатывает уже успешные шаги при ошибке следующего. Каждый шаг команды должен завершать свою мутацию полностью либо возвращать ошибку до неё.
- `CommandFieldType` сейчас описывает примитивные и плоские поля; вложенная запись массива с `{EntityId, Transform}` не представлена. JSON transport в проекте отсутствует. Нельзя считать составной payload уже сериализуемым внешним AI/API-контрактом только потому, что C++ CommandRegistry его примет.

## Рекомендация для первой реализации

Ограничить начальную функцию массового Inspector только Transform выбранных сущностей:

1. Inspector показывает размер выделения и три группы local position, Euler rotation и scale. Каждое поле явно обозначено как локальное относительно родителя.
2. Если соответствующие значения отличаются, показывать видимое mixed-состояние, не подставлять значение primary entity как будто оно общее.
3. Редактирование одного поля выставляет новое значение для всех выбранных сущностей, сохраняя остальные компоненты каждого их local Transform. Например, изменение X position не меняет Y/Z, rotation или scale каждого объекта.
4. Draft фиксирует SceneId, точный набор EntityId, их Transform ComponentId и исходные значения. Если selection, scene или одно из значений меняется до Apply, draft инвалидируется/пересчитывается, а не частично применяется.
5. Добавить отдельную транзакционную typed-команду, условно `entity.set_transforms`, с записью на каждый целевой объект `{EntityId, полный новый local Transform}`. Полностью проверить весь payload и каждую новую Transform на копии Scene до первой мутации; пропускать no-op entries; Apply/Undo/Redo должны быть одним history item и сохранять Transform ComponentId.
6. До реализации определить каталог/schema representation для структурированного массива записей. Не раскладывать пары и девять полей в неявные параллельные массивы и не кодировать EntityId через floating-point `NumberArray`. Если внешний JSON/AI transport будет добавлен позже, он обязан иметь отдельный проверяемый codec для этой записи.
7. На первом срезе не включать массовое добавление/удаление компонентов, свойства имени, материалы, assets, ScriptBehavior или world-space/gizmo операции. Для них нужны отдельные правила совместимости и выбора.

## Зависимости и риски

- Зависимости: существующий multi-selection 09.3n, обязательный Scene Transform, typed CommandRegistry, transaction history, Inspector dirty/save path, localization и smoke infrastructure.
- Главный риск — принять локальные координаты за мировые при сущностях с разными родительскими цепочками. UI и команда должны явно сохранить local-space семантику; world pose может различаться после одинакового local delta.
- Второй риск — устаревший draft после изменения selection/Scene. Нужны snapshot/stale checks для всех участников, а не только primary объекта.
- Третий риск — частичное изменение сцены при одном невалидном объекте. Команда должна предварительно проверить весь набор на копии и иметь единый rollback/Undo.
- API риск — пока нет структурированного schema field и JSON transport. Любой новый enum/schema type описывает каталог, но не создаёт сам по себе внешний сериализатор.
- В первом срезе не требуется новая внешняя зависимость или изменение формата Scene.

## Рекомендуемая проверка реализации

- Unit: классификация общего значения и mixed-state по каждому из девяти Transform-полей; draft сбрасывается при смене Scene или набора/порядка selection.
- Integration: каталог новой команды и структурированный payload; dry-run не мутирует; неизвестный/повторный ID, отсутствующий Transform, нечисловые значения и невалидный target отвергаются без изменения любого участника; один Undo/Redo меняет всю группу; no-op не добавляет историю; сохраняются все Transform ComponentId и неотредактированные поля.
- Editor smoke: выбрать два объекта, у которых local Transform отличаются, увидеть mixed-state, изменить одно поле, убедиться, что остальные поля у каждого объекта остались прежними, выполнить Undo/Redo, сохранить и перечитать сцену. Отдельно проверить устаревший draft после смены selection.
- Regression: существующий одиночный Inspector/`entity.set_transform`, AI review, Hierarchy group drag, Scene serialization и localization.
